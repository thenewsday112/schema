Import attributes are metadata that are attached to import statements. Typically, they’re meant to instruct runtimes and bundlers on how to interpret the content of an import, as well as the shape of the resulting module. For example,

Everything in the object following the with keyword is an import attribute. Environments like browsers can’t simply decide how to deal with an import based on file name extensions like .json. Specifying type: "json" tells whatever runtime that someData.json needs to be interpreted as a JSON file, parsed out, and provided via a default import (in our example above, that’s myData).

The type attribute has become the de facto way for runtimes to customize this behavior. ECMAScript (JavaScript) has a proposal that allows code to specify type: "text", which returns the import’s contents as a string.

There is also a proposal for type: "bytes" to return a Uint8Array of raw bytes.

Browsers have also allowed importing CSS files as CSSStyleSheets with type: "css" for a few years now.

To support importing these files, people might use ambient module declarations in TypeScript using a wildcard pattern (e.g. *.css).

This is okay, but it doesn’t work for all environments as it doesn’t account for import attributes at all.

You might ask why this is an issue – at first glance, it seems like the only problem is that it just allows people to accidentally leave off an import attribute.

But that is still a problem worth fixing. Another issue is that it becomes repetitive. With import attributes, the entire issue is that the runtime cares about the attributes, not the file extension. We shouldn’t have to re-declare a pattern for both .txt and .md files if both were going to use type: "text".

But a major issue is that runtime environments may support different import attributes entirely, and may act differently depending on whether they’re present. For example, bundlers might use a build-time feature called CSS Modules as the default behavior when importing .css files, but specifying the browser-supported type: "css" in the import statement will override this behavior and ensure the .css file is brought in as a CSSStyleSheet object.

That’s why TypeScript 7.1 introduces support for import attributes in ambient module declarations. You can now declare the following in your TypeScript projects, get an error if you try to import a file without the required import attributes, and get the correct type based on the import attributes.

Note that imports matching these declarations are not validated against files on disk. As is currently the behavior when an import matches an ambient module declaration, failed lookups will be reported at runtime or during a bundler’s build process.

Also note that these declarations are not shipped as part of the TypeScript built-in libraries. We recommend libraries not include them in their published packages, and end-users will need to declare them in their own projects if necessary. That will provide end-users with flexibility on how the global scope is configured (e.g. lib.dom.d.ts versus @types/node) and will prevent conflicts with built-in declarations in the future.

For more information, see our implementing pull request here.

Source phase imports are a proposed new feature in ECMAScript. The feature introduces a new source modifier/keyword that follows the import keyword. Only default imports can be written with import source.

The idea with this feature is that when we use import source, we’ll get back an object that represents the module after it’s been parsed and analyzed by the runtime, but before its imports have been loaded (and therefore, before they have been validated or linked against other modules, and before any code contained in the module can run). This object on its own is kind of “inert” – it’s an instance of something called an AbstractModuleSource which is eventually meant to be imported or instantiated.

For WebAssembly (wasm) imports, that object will be an instance of a WebAssembly.Module. What’s useful with these objects is that they can be passed directly into WebAssembly.instantiate.

WebAssembly source imports are already supported in recent versions of Node.js.

At the moment, you can’t do much with a source import of a JavaScript file. The spirit of the proposal implies at some point we might be able to pass a JavaScript module source directly into an import() call.

Another part of the idea with JavaScript source imports is that, over time, we may gain other features that will allow us to be able to customize behavior around how modules are loaded and instantiated, similar to how we did with WebAssembly.instantiate above. But we’re not there yet, and in fact, many environments and tools still don’t currently support JavaScript source imports in the first place.

Source imports aren’t limited to import statements though. You can also perform a dynamic source import as well via the import.source meta-property function.

Source imports retain identity. That means you can use them in Maps and Sets, or compare against them reliably.

When using import source, every imported module has the type AbstractModuleSource, a new global type in lib.esnext.d.ts. You must have an appropriate --module setting (i.e. esnext, nodenext, or preserve) to use source imports, as well as the appropriate esnext option in --lib or --target.

This feature was implemented thanks to the work of Oleksandr Tarasiuk.

TypeScript 7.1 now supports es2026 as a stable --target and --lib option. Only lib additions are significant, as declarations have been added, or moved from esnext as proposed features have stabilized in ECMAScript 2026.

The work of creating the new targets, as well as many of the declaration files themselves, was done thanks to Oleksandr Tarasiuk.

By default, TypeScript’s APIs will operate over the host file system. That means that it will hit files “on disk” unless we say otherwise.

In our earlier example, we created a (partial) virtual file system with createFileSystemWithLib and specified only the file in our program that we cared about. There are some ways to control how files are observed over these layers. For example, removedPaths can block out requests from the underlying system.

If you need to provide some level of file watching, that currently needs to be done separately. File creations/deletions/modifications need to be provided via the fileNotifications option in snapshot.update(). Any modifications that occur that aren’t in the host file system need to be provided with another file system layer.

TypeScript has long had powerful checking and tooling for TypeScript and JavaScript code; however, lots of developers use specialized file types for writing out their components. For example, Vue.js has regions of HTML, JavaScript, and CSS all within a single .vue file, along with embedded regions for JavaScript in that HTML. The same is true for libraries like Astro, Ember, Svelte, and others – these frameworks follow a similar way of declaring their components. At some point, a project called Volar emerged to provide TypeScript tooling for these single-file component formats to provide a seamless development experience in the editor. Volar surfaces errors, code completions, navigation, and more by using TypeScript’s language services, and has been able to extend its capabilities to other formats, such as MDX files.

Unfortunately, one of the challenges with Volar was that TypeScript lacked some of the APIs to easily provide a cohesive experience. For example, while Volar’s model shined for editor support, command-line type-checkers for these other file formats could not really use Volar because they integrate with completely different APIs from TypeScript. Another issue was the fact that Volar either had to embed TypeScript as a subcomponent and completely take over the editor experience, or it had to use awkward workarounds to integrate with the existing TypeScript tooling given limitations in our APIs. With TypeScript 7.0, we took an opportunity to rethink how the toolset could better support formats that embed JavaScript and TypeScript code. In fact, with TypeScript 7.1, Volar’s core model is now a first-class citizen.

When platform teams manage containerized applications at scale on Amazon Elastic Container Service (Amazon ECS), configuring ingress networking for each service often becomes a bottleneck. For every new service, teams must provision and connect Application Load Balancers (ALBs), AWS Certificate Manager (ACM) certificates, AWS WAF web ACLs, and security groups, then keep those resources in sync as services scale, update, or operate. This per-service overhead slows down deployment velocity and increases the risk of configuration drift across an organization.

Today, we’re announcing Amazon ECS Gateway, a new account-level resource that simplifies ingress networking for containerized workloads by dynamically provisioning and managing the necessary infrastructure on your behalf, with all resources created directly in your account.

ECS Gateway introduces a clear separation of responsibilities between platform teams and application teams.

ECS Gateway offers host-based routing using ALBs and enables up to 25 services to share a single ALB, optimizing infrastructure costs. ECS manages the full lifecycle of the underlying infrastructure, provisioning the first ALB when your first service connects, adding more ALBs as capacity is reached, and removing them when no longer needed. Each service receives a unique DNS hostname, giving your teams a ready-to-use endpoint the moment provisioning completes.

A first look at ECS Gateway In the ECS console, platform team can create a gateway and sets its configuration. The infrastructure role is an IAM role that ECS assumes to provision and manage networking resources such as ALBs, security groups, and certificates in your account. To create a gateway, provide a gateway name and select an infrastructure role. You can optionally associate the gateway with ECS clusters during creation or later.

Choose a load balancing scheme, either public or VPC-internal traffic routing. Under Additional Settings, you can also set up a listener, port, maximum count of load balancers the gateway can scale to, and a web ACL lets you protect your web applications. Some settings, including the name, scheme, VPC, subnets, IP address type, listener protocol and port cannot be changed after gateway creation.

Using AWS Command Line Interface (AWS CLI), call CreateGateway with a name (unique per account), an infrastructure role, and a configuration object. No infrastructure is provisioned until a service connects with a gateway connector.

Once the gateway is created, you can take a look at the detailed configuration, gateway routes, load balancers, and associated clusters.

Now associate the gateway with one or more clusters (many-to-many), to make it available to ECS services on those clusters.

ECS Gateway:Behind the scenesA gateway can be associated with up to 10,000 clusters, and a single cluster supports up to five gateway associations. This many-to-many relationship gives platform teams the flexibility to share a gateway across environments or assign multiple gateways (for example, public and private) to a single cluster.

Platform teams can control access by choosing which gateways to associate with which clusters. For additional control, use IAM policies to restrict who can deploy services to specific clusters.

Application teams add the gateway connector to each service definition in CreateService or UpdateService. If you have an existing ECS service with its own load balancer, you can adopt ECS Gateway incrementally by calling UpdateService to add a gateway connector. Both ingress paths remain available, allowing you to validate the gateway connection before removing the existing load balancer configuration.

At deployment time, Amazon ECS evaluates the gateways associated with the cluster and connects the service to every compatible gateway. A gateway is compatible when its access type matches the service’s connector filter, it is in the same VPC as the service, and it covers all Availability Zones used by the service’s configured subnets.

For each connection, Amazon ECS assigns the service to an ALB with available capacity and provisions the per-service resources: an ACM certificate, a unique DNS hostname, a listener rule routing traffic for that hostname to the service target group, and a service security group allowing inbound traffic only from the ALB security group. If no existing ALB has capacity, ECS creates a new one (up to maxAlbCount referring to quota limit). Once provisioning completes, the gateway route becomes ACTIVE, and the service URL is ready to receive traffic.

Itâs worth taking a few minutes to read about how Anthropic's prompt cacheÂ works. It works by caching parts of the prompt that have already been computed by the large language model (LLM). These are known as prefixes, because they only work on the messages at the start of the conversation, not mid way through or the end. A prefix is only stored where a cache breakpoint ends it. Ontology-Driven Observability: Building an End-to-End Knowledge Graph at Netflix Scale

📅 Oct 16, 2026  |  Category: Technology  |  Read Source →

Prasanna Vijayanathan, Renzo Sanchez-Silva

When Jake Paul and Mike Tyson stepped into the ring in November 2024, we delivered the fight to roughly 65 million concurrent streams. On an ordinary day our infrastructure takes in more than 2 billion requests and handles upwards of 38 million real-time logging events every second. At that scale, the whole picture doesn’t fit into a single engineering team’s head or onto a single dashboard. With more Live content, Podcasts and real-time streams, our need to understand and update our systems as quickly as possible becomes imperative to provide a good user experience. Understanding the system at this scale and within the time constraints we have, often becomes a daunting exercise in finding a needle in a haystack, in a dark jungle, blindfolded.

This post is about that search for the needle.

The Four hours before a fix

Consider a regression of the kind we see in a given week. The home screen where you see the list of lists of movies, starts taking about 1.5 seconds longer to render. An alert fires. And then we go looking for what caused this issue and how do we fix it?

As it so happens, a regression on the application could be related to anywhere in the system — a client app regression from a new version deployment or A/B test rollout, a load shedding in the infrastructure, a GraphQL query responding with bad data because of a service rollout 6 hops downstream, are all suspects at this point. So, answering “what caused the issue?” needs insights from across the system, and this involves combing through layers of data in a meticulous manner.

The MELT Layer

“What caused the issue?”

Metrics, events, logs and traces, or MELT, in the industry’s shorthand, are the right raw materials for such an investigation, and each of them answers roughly a quarter of the question. We collect observability data across these four pillars, unified into a single observability data layer. This lets us observe our systems in real time, across what our users are experiencing, how our applications are doing and what our backend infrastructure and services are processing and responding to.

The timeline of an investigation

So how long does it take to investigate an issue, figure out the root cause and fix it, so our users stop running into this issue again?

In our chosen example, four hours. Very little of it went into computing anything difficult. Most of it went into reconstructing relationships that our observability systems already knew but we had never written down anywhere a human or machine could simply read and discover.

The disagreement underneath

The instinct here could have been, around 2023, to reach for more data or better dashboards, and while both help at the margins, neither addresses what makes these investigations slow.

It’s 2026 now, so we might say, “hey, agents”, but without the right context delivered to the agents, AI systems hallucinate, and especially when teams are on-call and need a fix “now”, we cannot let inaccurate agentic analysis lead us down the wrong path. We need the right needle, not any needle.

Each of our systems is internally coherent and externally isolated. Atlas, our telemetry platform, knows applications and their time series. Radar, our alerting system, knows thresholds and firing history. incident.io knows severities and responders. PagerDuty knows rotations. Spinnaker knows what shipped and when. And our Slack history knows, in a form no query engine can reach, which engineer solved something very similar last quarter and what they found.

The difficulty is that they do not agree on what they are talking about. A thing that is an application in one system is a service in a second and a cluster in a third, with names differing by a suffix, a casing convention, or a rename only a couple of people remember (SMEs, ring a bell?). Joining across them requires a human carrying the mapping in their head, and that person becomes the bottleneck in such cross-domain investigations. The hard part of end-to-end observability is probably better understood as a data modelling problem.

What we lacked was an explicit, machine-readable agreement about the entities in our operational world.

The Ontology

This agreement has a name: an ontology. Ontology is a formal specification of types, the properties they carry, and the relationships they may have. Its unit is the triple, one fact expressed as subject, predicate, object. Consider the following example triples.

api-gateway   rdf:type       ops:Application .
api-gateway   ops:ownedBy    "Team Bedrock" .
api-gateway   ops:deployedIn "us-east-1" .

INC-5377      rdf:type       ops:Incident .
INC-5377      ops:affects    api-gateway .
INC-5377      ops:severity   "SEV 2" .

In the example here, we have already encoded six facts, and can answer in one query, a question that used to span three tools.

“Which incidents affected applications owned by Team Bedrock in us-east-1?” is a single query in place of looking up incidents, Spinnaker and Radar.

We call our ontology layer, The Observability Ontology. It acts as the schema, rule set and shared agreement that standardizes how different systems understand entities like applications, services, incidents, deployments, etc.

We built it on the W3C stack for this: RDF for the data model, OWL for the ontology, SHACL for validation, and SPARQL for querying. These standards are well specified and widely implemented, which keeps the model portable across graph stores.

The data from the ontology itself, is stored as a knowledge graph, persisted to QuipuDB, our homegrown RDF graph database, a distributed quad store based on redb, a Rust-based embedded key value db. Data here is generated by parsing raw telemetry, logs, and incident discussions into triples (subject-predicate-object facts).

Every harvest also produces a full Turtle serialization for archival, making it human-readable and diff-friendly, which has proven more useful for debugging than we expected.

There are two decisions about this ontology that mattered while we built it, so they’re worth sharing.

The first is that we refused a generic Service type. “Service” means four different things across our tooling, so applications resolve to exactly one type, ops:Application, and every one of them is validated against our software catalog of roughly 49,000 entries before the entity is created. Unvalidated strings like usernames, team names, dependency names scraped from network topology, never become applications. We also cap dependency edges in both directions, because one popular service can carry thousands of reverse dependencies and would otherwise dominate the graph.

The second decision concerns what we chose to model. Incident chat carries the reasoning behind an incident. The hypotheses tried and discarded, the mitigation that worked, who knew why, is all context in the incident’s Slack channel and that knowledge evaporates when the channel goes quiet. So a 200-message, 50-person, 15-service incident channel becomes a structure, converting the operational chaos of an incident into ordered triples:

Creating determinism from non-determinism

Building this graph means using tools that are inherently stochastic. LLMs summarize discussions. Fuzzy matching resolves service names. A probabilistic engine proposes causal chains. None of these produce the same output twice with certainty, but what comes out at the end of our system is a deterministic graph that answers a SPARQL query the same way every time.

The ontology is the mechanism that creates this determinism through its pipelined approach. We think of the pipeline as a ladder that drives entropy down, where entropy means the proportion of information still trapped in unstructured form. For example, at the start of this pipeline, an LLM could say anything, but it cannot emit a triple that violates the type system. We constrain the output space tightly enough and a stochastic process yields a deterministic contract:

# The model may produce any prose. Its output MUST fit these predicates:
category  IN ["incident", "question", "discussion", "decision"]
sentiment IN ["positive", "neutral", "negative", "urgent"]

# Result — a deterministic triple:
thread:123  slack:category          "incident" .
thread:123  slack:isIncidentRelated "true"^^xsd:boolean .

There are five layers that get us down this ladder. Any single step of this ladder is non-deterministic. But in aggregate, the chain becomes deterministic. That inversion is the whole trick. We describe them below:

Enrichers: Agents as entropy reducers

We use what we call, enrichers, to reduce entropy across the knowledge graph. Dozens of enrichers run over the graph. Each one of them takes noisy input and emits typed triples, and each reads what earlier enrichers wrote. The contract for an Enricher is deliberately narrow:

class Enricher:
    async def _enrich_async(self, ...):
        raw    = await self.fetch(...)      # 1. read noisy input
        result = self.analyze(raw)          # 2. process (may be stochastic)
        graph.add((uri, RDF.type, OPS.X))   # 3. emit TYPED triples
        graph.add((uri, OPS.pred, Literal(result.value)))
        return EnrichmentResult(success=True, triples_added=count)

Three invariants that are standard across the enrichers:

  • every entity carries an rdf:type,
  • every URI follows a single naming scheme, and
  • the catalog gates every ops:Application.

Two operational choices are worth naming here, as well. The enrichment pipeline runs sequentially — load the graph, add triples, and save.

This sequencing removes an entire category of race conditions at a cost in wall-clock time we are happy to pay. And calls out to external systems like metrics, logs, events and the rest could be best-effort, so a slow downstream API doesn’t block the graph harvest, albeit some degradation. To that end, we are also working to translate these separate systems into the ontology, such as the Metrics Ontology and the Alerts Ontology, so everything could be queried from the Ontology itself.

The Correlation Engine: finding the correlation chains

The correlation engine assimilates the vast number of signals from diverse input sources and condenses them into causal or correlatory chains of events. Today, the engine reads thirteen signal types, including log errors, metric anomalies, slow and failed traces, alerts, incidents, deployments, config changes, experiments, autoscaling, commits, end-to-end bottlenecks, and error patterns. It then searches for paths among them. Some ordered pairs are known to be causal and carry a high prior weight. For example, deployment before log error, config change before metric anomaly, failed trace before incident, and so on. Others, which show high correlation are considered correlation chains. Such chains are scored on temporal proximity and severity, inside a ten-minute window, with anything under 0.6 confidence getting discarded.

The role of the engine here is to propose with evidence, not to make conclusions. Hence, the engine stores its chains along with the graph records that were used to create them.

A 0.87 chain in the above example, is a strong hypothesis for a human or an agent to check, and the graph records the confidence alongside the claim so that consumers can understand why a chain is what it is and weigh their options to make decisions.

The knowledge flywheel

Each harvest cycle turns the same four steps, and each rotation leaves the graph richer for the next. This is the Knowledge Flywheel, leading to continuous enrichment and improvement of the context about our system, stored in the knowledge graph.

Observe collects the signals. Enrich adds typed triples. Infer finds patterns invisible in the raw data. Adapt feeds knowledge back, so that established patterns become detection rules. The compounding result of the four phases leads to a self-improving system. A causal chain discovered in one incident becomes a known pattern for the next, and the ontology gradually stops being a schema and starts being a memory.

Consider the example above. When we first see an incident in api-gateway caused due to a timeout and resolve it, we convert this knowledge into entries to the ontology. This becomes encoded knowledge. As we go through multiple cycles of this encoding, the graph starts learning patterns. After N cycles, patterns become wisdom — “api-gateway deploys cause 40% of SEV-2s” and “30% of deployment issues in api-gateway come from Connection Timeouts”. Surface this as an insight and we proactively start reducing incidents, not just react quickly to new ones.

Putting the graph to work

On top of the graph sits AutoRCA, our internal agentic AI solution, built with a set of specialist agents coordinated around one question. Walking the home page regression from the top of this post, the agentic system’s reasoning chain might look something like this:

Each specialization to the inputs is built by people who understand their respective domain deeply. That division of labour only works if the specialists can pass findings to one another without having to agree on the terms of communication or even have knowledge of each other. The ontology acts as the interface. Each specialist learns one vocabulary — the graph’s. A team writing specialized use cases for how they use traces record their findings as triples about an ops:Application, the logs specialization reads triples about that same ops:Application, and neither needs to know the other exists. A new specialist learns the same vocabulary once and can immediately read everything the other six have written.

Set against the investigation we opened with, the change is narrower than it might sound. The alert still fires at 3:30pm, an engineer still has to weigh the evidence, and the fix still has to be written by someone who understands the code. The hour or two that used to go into assembling context — finding the owning team, reconstructing what shipped, correlating information from different parts of the system, recalling that something similar happened last quarter — all that work is the part the ontology and the graph absorbs. We are early enough that the ranked hypotheses are sometimes wrong, which is why each one carries the evidence that produced it. But when the engineer now starts the investigation, they are already holding the picture that used to take half an afternoon to assemble.

If you want to build one of these

A fair amount of what we have built, we learned by getting it wrong first. Based on this experience, these are the principles we would carry into a second attempt.

  • Model identity before anything else. Choose one authoritative catalog per entity kind and validate against it before creating an entity.
  • Treat the ontology as code. Version it, review it, test it, and let changes arrive as pull requests. Treating the ontology as code lends itself to agentic development and lets teams scale and contribute to it.
  • Separate concepts from instances. Concepts change on a human timescale and instances change continuously, conflating them makes both harder to evolve.
  • Build on open standards. RDF, OWL, SHACL and SPARQL are specified, implemented many times over, and portable. A bespoke graph model ties a future consumer to one implementation.
  • Constrain stochastic tools with a type system. This is the principle we would defend hardest. Models are useful precisely where determinism is impossible, and a sufficiently narrow output contract converts their output into something a query engine can trust.
  • Make enrichment best-effort and ordered. A slow dependency should utmost degrade the graph, never block it. And ordering enrichers so each builds on the last buys more accuracy and that’s worth the tradeoff with parallelism that buys speed.
  • Model human reasoning alongside machine telemetry. The most valuable edges in our graph came from discussion. Telemetry records what the system did, discussion records what people understood and interpreted. The reasoning is more valuable to store and serve as wisdom when we need it.
  • Keep humans as the approvers. Let agents propose fixes, enrichers, and ontology changes, and route every proposal through a review process with humans in the loop.

What comes next

The graph makes three things possible. First, automatic root cause analysis, where a regression arrives with a ranked set of graph-backed hypotheses attached. Next, automated remediation, where a sufficiently confident diagnosis carries a proposed action like a targeted rollback, a traffic shift, a code change. And eventually infrastructure that heals itself, acting on a predicted failure before members feel it.

Alongside this, we plan to integrate the Observability Ontology with Upper, the domain-modeling language at the heart of Netflix’s Unified Data Architecture (UDA). Upper lets teams describe business and system domains as interconnected, machine-readable models and preserve their meaning and constraints as those models are projected into concrete schemas and systems. This integration would connect operational concepts such as applications, alerts, deployments, and incidents to the broader set of domains modeled across Netflix, giving engineers and agents a shared semantic layer for querying, validation, and reasoning. We will begin with a proof of concept that models incidents in Upper and use what we learn to determine where the two systems should converge.

As you navigate and edit code, your editor (such as VS Code, Neovim, or Emacs) and a language server (like gopls) engage in a continuous JSON-RPC exchange to provide features like autocomplete, hover documentation, diagnostics, and code actions.

Today, almost every code transformation in the LSP is like a function of no parameters: you trigger the operation, and the server immediately computes the edits. (Renaming a symbol is the sole exception: because it is a function of one parameter, the desired new name, it required its own dedicated PrepareRename RPC in the protocol.)

The language server must deduce the user’s intent from context alone, namely the cursor position and the enclosing syntax tree. When that context is not enough, the server is forced into one of two choices: apply a one-size-fits-all default, or refrain from offering the transformation altogether. The limitation lies not in gopls’s ability to compute the necessary edits, but in the LSP’s lack of a mechanism for language servers to ask the user for input.

For many transformations, this parameterless model works well. But many others need additional input from the user: which struct tags to add and in what naming convention, which interface to implement, which file to move a declaration to. Without a way to ask, gopls could only guess—“Add struct tags”, for example, always produced json tags in camelCase—or not offer the refactoring at all. With interactive refactoring, language servers can now easily provide new operations with one or more parameters.

While some language extensions have worked around this limitation by embedding custom, language-specific dialog logic directly into individual editors, doing so leaves behind other editors (such as Neovim and Emacs) that stick strictly to the LSP with minimal custom client code. More importantly, editor-specific workarounds go against the fundamental purpose of the LSP: to decouple language-specific features from editors so that each server improvement benefits every client.

MCP standardized tools. Now we need the infrastructure around them.

📅 Oct 15, 2026  |  Category: Technology  |  Read Source →

Developers can now connect models to repositories, databases, browsers, observability systems, internal APIs, and dozens of other tools through a shared protocol. Claude Code, Cursor, Codex, VS Code, and a growing list of other clients all speak it. Vendor-hosted endpoints exist for GitHub, Linear, Notion, and many others. The Tier 1 SDKs are approaching half a billion downloads a month.

That is a real achievement. For years every AI application built its own tool-calling layer. MCP gave the ecosystem a common interface. Once a server exists, multiple agents can use it without custom glue. That alone is worth the effort.

But after building around MCP for coding agents, I started noticing something else. The protocol was becoming standardized faster than the infrastructure around it. Connecting a tool was becoming easy. Running that system reliably across real users, real credentials, and real work was not.

The protocol solved a specific problem: how can an AI model talk to tools through a common interface? The next set of problems is different. How do we make thousands of those interactions reliable, secure, efficient, observable, and straightforward to deploy?

The happy path looks simple. An agent talks to an MCP client, which talks to an MCP server, which calls a tool that talks to an API or database. In a demo, that is often all you need.

In production, the picture changes. You have multiple agents, multiple users, many MCP servers, credentials that must not leak, rate limits, permissions that differ by person or by task, failures, retries, logs, tool schemas that change, context constraints, and machines that are not identical. The mental model becomes something closer to agents and clients sitting in front of authentication, routing or gateways, then a set of MCP servers, then the actual systems those servers touch. Every one of those layers can fail independently.

A concrete example: an agent that reads documentation and fails once is annoying. An agent that creates cloud resources, writes database records, or opens pull requests and fails halfway through is a different problem. Partial work, inconsistent state, and the need for idempotency or compensation become real requirements. The protocol does not magically supply them.

One pattern I kept seeing is infrastructure duplication. Developers and teams repeatedly build authentication, deployment, connection management, retries, logging, secret handling, health checks, access control, simple registries, caching, and rate limiting. The same pieces appear in different codebases because the protocol standardizes the message format, not the operational concerns around it.

This is not unique to MCP. Earlier infrastructure transitions followed a similar shape. Once physical servers became painful enough, cloud abstractions matured. Once every application reinvented authentication, identity platforms matured. MCP may be entering a stage where managing dozens of individual local servers, each with its own configuration and credentials, starts to feel like the old way of doing things. Whether the eventual abstractions live in agent runtimes, cloud platforms, gateways, or somewhere else is still open. The duplication is already visible.

Local servers over stdio are easy to understand, close to the user, and naturally connected to local files and processes. They were the perfect way to experiment. Local execution also avoids many of the authentication and multi-tenant problems that appear once the server moves onto the network.

Team-scale usage exposes the limits. Everyone needs installation and configuration. Versions drift. Credentials live on different machines. One developer’s server can break differently from another’s. Onboarding becomes repetitive. Observability is fragmented because each machine is its own island. Remote or hosted servers address some of those problems, but they introduce others: authentication that actually works across clients, latency, multi-tenancy, data handling, uptime, permissions, and questions of vendor dependence. Neither model is automatically superior. They solve different sets of constraints.

The July 2026 specification changes helped the remote case. Removing protocol-level sessions and the initialize handshake means a remote server can scale more like an ordinary HTTP service. That is useful progress. It does not remove the need for authentication, authorization, or operational discipline.

Coding agents need repository context. Naively giving an agent the whole tree creates token cost, irrelevant information, distraction, higher latency, and sometimes worse reasoning. Bigger context windows do not eliminate the problem. The question shifts from “how much can the model hold?” to “which context deserves to be there?”

This is where a lot of my early work sat. Hexum.dev began in part around making repository context more efficient, so the agent saw the relevant structure instead of a raw dump of files. On a published 24-task benchmark using MBPP and HumanEval, the measured context sent to the model dropped from 220,393 tokens to 27,352 (an 87.6% reduction) while still passing all official tests. The methodology is public. The number is less important than the observation: once you start treating context selection as a deliberate step rather than a dump, other constraints appear.

Developers talk about this constantly now under the banner of context engineering. Progressive or dynamic tool discovery is one response to a related problem: loading every tool schema from every server into the context on every turn. Client best practices now recommend deferring full definitions and providing a search-style meta-tool. The same guidance explains why: progressive discovery can dramatically reduce tool-definition tokens and can improve selection accuracy by keeping the model focused on a smaller set of relevant tools. The pattern is not universal yet, but the pressure is clear.

There is a point where giving an agent 50, 100, or several hundred tools becomes harmful rather than helpful. Selection accuracy can drop. Context fills with schemas the model may never need. Name collisions and vague descriptions make the problem worse.

Should every tool definition always sit inside the active context? Or should tools themselves be retrieved dynamically? Both approaches exist in the wild today. Static registration is simple when the surface is small. Progressive discovery, semantic search over tool descriptions, and gateway-style routing that exposes a smaller set are all being tried. The protocol itself is moving in this direction through progressive discovery guidance and related work. What remains open is how much of the selection logic lives in the client, in a gateway, in the server, or in the model’s own tool-use training. Least privilege also matters here: an agent that can see every tool is an agent that can be tricked into calling ones it should not have access to.

MCP security is not the same as ordinary API security. An agent can read untrusted text, interpret it as instructions, call tools, and mutate external state. That creates surfaces that look like prompt injection, confused-deputy problems, over-broad permissions, malicious or poisoned tool descriptions, secret leakage through arguments or results, and supply-chain risk from the servers themselves.

None of this means the protocol is inherently insecure. It means that once natural language can cause software to invoke real capabilities, the trust boundaries and permission model become critical. Least privilege, explicit approval for destructive actions, careful handling of tool results as untrusted input, and authentication that survives the full path from client to server to backend system all matter more than they do for a conventional API. A 2026 measurement study of 7,973 live remote MCP servers found that 40.55% exposed tools without authentication. That is a deployment problem, not a protocol problem, but it is the problem teams actually hit.

A human using software notices an error and stops. An autonomous agent may continue. That changes the requirements around retries, idempotency, timeout behavior, partial failure, and validation of tool results. Observability becomes more important because you may need to reconstruct what the model believed, which context it saw, which tools it knew about, which one it selected, what arguments it generated, what the tool returned, and what it did next.

Standardized telemetry is starting to appear. OpenTelemetry’s GenAI semantic conventions include MCP-related spans and attributes. Work such as SEP-414 reserves space in _meta for W3C trace context so traces can cross the MCP boundary. The official Python SDK now emits OpenTelemetry spans by default. Whether this becomes the default way teams debug agent-tool systems is still early, but the demand is obvious once agents move past demos.

At first I thought one of the main problems was context efficiency. Hexum.dev’s early work on shrinking repository context for coding agents reflected that. Once you optimize context, you run into tool selection. Once you expose tools, you run into deployment and configuration. Once tools are remote, you run into authentication and permissions. Once agents become more autonomous, reliability, security, and observability move to the front. The realization was that MCP is not merely a protocol problem. It is becoming an infrastructure category.

Hexum.dev today is a hosted remote MCP endpoint for coding agents. Its scope grew as we ran into adjacent problems around context handling, architecture checks, and controlling agent behavior. The agent still lives in the editor the developer already uses; Hexum.dev sits around specific parts of that workflow. Building it did not eliminate the surrounding problems. It made them concrete.

There is one lesson from building Hexum.dev that has nothing to do with protocols.

Most of building is uncertainty. Things fail, direction changes, and you spend a lot of time on ideas before anyone validates them. Having friends who listen, encourage you, and challenge you when needed matters more than founders often admit. Yuchen and Pranav have been two of those people for me. They are not building Hexum with me, but they have listened to countless ideas and made the uncertain stretches easier to keep moving through.

A possible future stack looks something like this: models and agents at the top, agent runtimes and MCP clients beneath them, then an infrastructure layer that handles routing, authentication, permissions, context management, tool discovery, caching, observability, policy, and reliability, then the MCP servers themselves, then the databases, APIs, code, and SaaS systems those servers touch.

This is a hypothesis, not a certainty. Some of those capabilities may end up inside model providers, inside agent runtimes, inside cloud platforms, inside gateways, or inside individual MCP servers. The boundary is not fixed. The interesting part is that the protocol’s success is forcing the question. Once tool interoperability is taken for granted, the remaining work is everything required to make that interoperability production-grade.

MCP’s biggest achievement may be that developers are beginning to take tool interoperability for granted. That is what successful standards eventually do. They make a previously hard problem feel ordinary.

Standards rarely eliminate infrastructure. They move the infrastructure problem somewhere else. HTTP standardized how systems communicate, but we still built CDNs, load balancers, API gateways, observability platforms, identity systems, and cloud infrastructure around it. MCP may follow a similar path. The protocol gave agents a common language for tools. Now we have to build everything required to make that language reliable at scale.

The interface is no longer the hardest part. The systems around it are.
