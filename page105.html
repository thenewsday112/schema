What's new in Swift: July 2026 Edition

📅 Oct 30, 2026  |  Category: Technology  |  Read Source →

Welcome to “What’s new in Swift,” a curated digest of releases, videos, and discussions in the Swift project and community.

Swift is built by contributors working on far more than the language and compiler. Alexander Sandberg reflects on what that kind of contribution looks like, and why there’s a place for you too:

Hi, I’m Alex. Four years ago I joined the Swift Website Workgroup to help care for the website you’re reading this on. I was still fairly new to the Swift community then, but I wanted to get involved somehow and make a difference.

Contributing to Swift sounds like it should involve working on the compiler or writing and reviewing language evolution proposals, but there’s a lot going on around the language itself too. What I actually spent my time doing was helping improve the site’s content and navigation, taking part in the big redesign, writing release blog posts, reviewing pull requests, and answering issues and forum posts. All of it is work anyone can learn to do, and all of it ends up in front of everyone who comes to Swift.org—which made even the smallest fixes feel worth doing.

The Website Workgroup happened to be my way in, but there are groups like it across the project—server, testing, Windows, Android, and more—each a handful of people looking after their part of the ecosystem. Whatever you’re good at or curious about, there’s probably a corner of Swift that could use your help. The community page is a good place to start looking, and the people you’ll meet are some of the friendliest I’ve come across in open source.

After four years, I’ve stepped away to focus on other things in life. Thank you to everyone I got to work with over these years! I’m leaving the workgroup, but not the community, and I’ll still be around helping push Swift forward where I can.

For more information about workgroups, the How we work page lists all workgroups. And on the Swift forums you’ll often see workgroups sharing open meetings if you’re looking to get involved!

  • Task Stealers, a new primitive in Swift Concurrency’s runtime, recently merged after generating the liveliest discussion of any PR in July. They change how work gets distributed across the cooperative thread pool, an under-the-hood change worth watching if you write concurrency-heavy code.

  • any-error-swift takes a different approach to error handling, offering a concrete, value-semantic, Hashable type that erases any Swift error, no Foundation required, and works on every platform Swift runs on.

Swift Evolution

The Swift project adds new features through the Swift Evolution process. These are some of the proposals recently accepted for a future Swift release.

Recently accepted:

  • ST-0025 Tag-based Test Execution Filtering - Swift Testing lets you annotate tests with named tags, and separately lets you include or exclude tests by regex using the --filter and --skip options, but there’s no way to combine the two and filter by tag. This proposal adds a tag: prefix to those options, so you can run commands like swift test --skip tag:uiTest to selectively run or skip tests based on their tags rather than relying on a consistent naming scheme.
  • SE-0513 API to get the path to the current executable - There’s currently no portable, reliable way to get the path to the currently running executable in Swift. This proposal adds CommandLine.executablePath, a new property in the standard library that provides a consistent way to get this value across all platforms Swift supports.

Recently accepted with modifications:

  • SE-0526 withDeadline - Asynchronous operations in Swift can run indefinitely, and implementing time limits manually using task groups and clock sleep operations is verbose and error-prone. This proposal adds withDeadline, a function that executes an async operation with a composable absolute time limit specified as a clock instant, canceling the operation if it hasn’t completed in time. It also allows multiple nested operations to share the same deadline, avoiding the drift that accumulates when relative durations are passed through call layers.

What's new in Swift: August 2026 Edition

📅 Oct 30, 2026  |  Category: Technology  |  Read Source →

Welcome to “What’s new in Swift,” a curated digest of releases, videos, and discussions in the Swift project and community.

Here’s an update from guest contributor Simon Leeb on Swift’s progress as a language for web scenarios:

Hi, Simon here! I am the creator of the elementary-swift project, a collection of packages born from a simple wish: I want to build web UIs in Swift and ultimately help Swift become a first-class choice for the web.

This journey began after I started using Swift for backend services. The web frontend, however, still lived in a separate ecosystem, and I really wanted it to feel as ergonomic, safe, and efficient as the Swift I was writing everywhere else.

That led to the creation of Elementary: a modern and efficient HTML rendering library with a familiar declarative API, built for the web. It integrates easily with frameworks like Vapor and Hummingbird, and has become a practical option for server-rendered web UIs.

Around that same time, years of community work in the swift-wasm project made compiling Swift to WebAssembly increasingly viable, while Embedded Swift was taking its first experimental steps. This made me wonder: “How hard can it be to use Embedded Swift and build a state-driven web UI framework that produces tiny WebAssembly binaries?” Turns out: quite hard, actually!

But it was too late. Despite my better judgment, I was in the middle of creating what is now known as ElementaryUI. Where Elementary renders HTML on the server, ElementaryUI runs in the browser itself. You can watch my talk at Swift@FOSDEM 2026 if you want to know more about the why, what, and how.

To showcase where the project is heading, I recently posted a small Full-Stack Swift on Cloudflare demo. It features Swift in the browser communicating with a Swift backend on an edge worker through shared message types. I hope it gives people a concrete sense of how much the core technologies and the surrounding tooling have advanced.

ElementaryUI is still young, with plenty left to build. Visit elementary.codes to try it, share feedback, contribute, or sponsor its development. Let’s work together and make Swift a first-class choice for the web!

Swift Evolution

The Swift project adds new language features through the Swift Evolution process. These are some of the proposals currently under review or recently accepted for a future Swift release.

Under active review:

  • ST-0029 Include additional issue metadata in event stream - Today, Swift Testing’s JSON event stream reports only bare-bones details when an issue occurs, making it hard to tell a thrown error apart from a manual Issue.record call. This proposal adds structured fields, including error, confirmationMiscount, exceededTimeLimit, and expression, so tools like Xcode and VS Code can show richer, more specific failure information.

Recently accepted:

  • SE-0544 Mutation and consumption in non-copyable type deinits - Non-copyable types that manage a resource, like a file handle or buffer, often need to run the same cleanup logic in their deinit that they use elsewhere, but until now self inside a deinit could only be borrowed, not mutated or consumed. This proposal lets a deinit mutate or consume its own stored properties directly, so existing cleanup methods can be reused instead of duplicated.
  • ST-0028 Revise Swift Testing’s Attachment/Encodable interop - Swift Testing lets you attach extra data, like a screenshot or JSON snapshot, to a test for inspecting after a failure, but attaching custom types previously required extra setup code and offered no way to choose the encoding format. This proposal adds new Attachment initializers that let you attach Encodable or NSSecureCoding values directly, picking the format or supplying your own encoder.

Recently accepted with modifications:

  • SE-0536 Package Registry Search - To use a package from a registry today, you already have to know its exact identifier, since there’s no standard way to discover packages within a registry the way other package ecosystems allow. This proposal adds an optional /search endpoint to the registry specification and a swift package-registry search subcommand, letting you find packages by name, scope, author, and other criteria, with support for qualifiers like author:"Mona Lisa Octocat" and searches that span every configured registry at once.
  • SE-0516 Iterable - Looping over a collection in Swift traditionally means copying out one element at a time, which doesn’t work for newer types that can’t be copied, like Span and InlineArray. This proposal introduces Iterable, a new way to loop over data without copying, and was renamed from BorrowingSequence and given support for typed throws before acceptance.
  • ST-0026 TaskLocal test trait - Task-local values are like settings, such as a feature flag, that apply only within a single task. Overriding one in a test previously meant writing a custom trait from scratch, but this proposal adds a .taskLocal(_:_:) trait that does it in one line, like @Suite(.taskLocal(FeatureFlags.$isEnabled, true)).

Introducing Vercel CI

📅 Oct 30, 2026  |  Category: Other  |  Read Source →

Coding agents are opening more pull requests than ever, and each one waits on CI before anyone can review or merge it. Most CI systems run the entire workflow on every push, even a one-line change. The more your agents push, the more time you spend waiting on CI.

Today, we're announcing Vercel CI in Beta. It runs only the tasks affected by your code change, and spins up only the compute those checks need, the same way Fluid compute scales with your traffic.

At Vercel, our CI now keeps up with our coding agents. Time from git push to "CI passed" is 2-6x faster than it was before.

Vercel CI uses Turborepo to understand your tasks and which ones depend on each other. It reads turbo.json, so if you're already using Turborepo, there's no separate CI config to write.

If you're not on Turborepo yet, add turbo.json and the turbo package. It works in single-package repos too.

Then tag the tasks you want Vercel CI to run.

"tags": ["ci"] is all you need to get started. No workflow YAML to maintain, no drift between your CI config and turbo.json, and Remote Cache is on by default.

When you or your agent push code, Vercel CI determines which tasks need to run based on the change. Tasks whose inputs haven't changed come from cache. The remaining tasks each run on their own machine, powered by Hive, Vercel's compute layer, and start as soon as their dependencies finish.

Vercel CI gives each task the compute it needs and nothing more.

To get started, follow the documentation or prompt your agent from your repo:

Set up Vercel CI for this repository. Run `npx skills use vercel/ci@setup` and follow the skill's instructions to select initial tasks, configure Vercel CI, and open a pull request.

Once set up, you or your agent can watch and inspect CI through the Vercel dashboard, Vercel CLI, or Vercel MCP. When something fails, go straight to the failing task, see what's blocked behind it, and open its logs, or search across recent runs to see whether a test has been flaky all week.

Vercel CI posts a check to your pull request on GitHub, so your existing branch protection rules can block merges on failure, the same way they do today.

Vercel CI has already completed nearly 8 million tasks across our own repositories and the private beta, and we're just getting started. We're working to keep shrinking the time between writing code and running it in production.

As we work toward general availability, we plan to add:

A vc ci CLI command for distributed execution before pushing code

Vercel CI is available in Beta today on all plans. Read the docs and try it on your repository.

Introducing Virtual Models on AI Gateway

📅 Oct 30, 2026  |  Category: Technology  |  Read Source →

Today, we are introducing Virtual Models on AI Gateway.

Virtual Models are an abstraction of the model string and configurations your apps and developers use. With a single virtual model ID, you can change and update models, configure fallbacks and priority, and enforce Zero Data Retention centrally. The virtual model configuration applies wherever the ID is used.

Assign a virtual model ID to an agent task, and pass it as the model string wherever that task is called. You can then change the model and settings behind the virtual model ID in AI Gateway, and your apps and agents will pick up the new configuration automatically, without code changes or redeploys.

In the last 90 days, 125 new models from more than 10 labs became available on AI Gateway. That adds up to about 10 a week. AI Gateway already makes switching a one-line change. You call any of those models by ID, and AI Gateway routes each request to a healthy provider and can fall back to others when one fails.

That one line still lives in your code, so switching usually means a redeploy.

Virtual Models move model selection and configuration to AI Gateway. You create an ID for a task, like vmc/coding-agent, and then configure the model and the settings it should use:

You can then use that virtual model ID as the model string wherever the task runs:

For coding agents like Claude Code, Codex, and others, connect them with vercel ai-gateway setup, then select your virtual model in each harness's model picker or configuration.

When a different model is available, including one from another provider, edit the virtual model. Every app and agent that calls vmc/coding-agent picks it up within a few minutes, with no code change or deployment needed:

An agent task like support ticket triage can run hundreds of times an hour and needs to be cheap. Other tasks, like legal contract review, may only run a few times a day, but require a high level of reasoning.

You can now give each task a purpose-built virtual model and easily evolve that model and configuration over time:

Settings such as fallbacks, Zero Data Retention, and tags stay with the virtual model when you switch models. Provider options apply per provider, so an Anthropic-specific setting stops applying when you point the virtual model at an OpenAI model. Review your provider options whenever you switch providers.

Before you switch a virtual model that serves production traffic, point a second one, like vmc/coding-agent-candidate, at the new model and run your evals against it. If quality drops after the switch, point the original back at the previous model.

Anyone on your team can call a virtual model, and team roles control who can make changes to it. Platform and security teams can centrally govern and test models and settings, while still easily giving teams access to new models as they are released.

Settings on a virtual model win over the same settings in a request, so callers can't override the provider order, fallbacks, or service tier you chose. For example, you can configure the fallback models for vmc/storefront-assistant centrally, and every app using that virtual model ID will use the same failover configuration, even if a request specifies different fallbacks.

If a virtual model requires Zero Data Retention or providers that don't train on request data, those configurations are enforced even if a request explicitly sets zeroDataRetention or disallowPromptTraining to false.

Tags on a virtual model replace any tags sent with the request, so spend lands on the task no matter how each app tags its calls. The Virtual Models page shows requests, spend, and success rate for each task.
