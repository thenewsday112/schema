Security teams have spent years trying to detect threats faster. AI is changing the harder part: how much time defenders have left to act.

Advanced AI models can now help attackers discover vulnerabilities, generate exploit code, and move through weaknesses faster than traditional security processes were built to handle.

The challenge is no longer just finding another vulnerability or generating another alert. It is knowing which exposures matter, what an attacker can reach, and which issues need to be fixed first.

That is the focus of next week's webinar, How to Build AI Threat Readiness Across Your Security Operations, featuring an expert from Wiz. The session will show how security teams can improve visibility, prioritize real risk, and shorten the path from detection to remediation.

Most security teams already have plenty of data. They have vulnerability findings, cloud alerts, identity signals, application telemetry, and threat detections. The harder problem is connecting those signals quickly enough to answer the questions that drive action.

Is this vulnerability reachable? Does the exposed asset contain sensitive data? Can an attacker move from it to something more important? Who owns the affected system? What should be fixed first?

When those answers live across different tools and teams, investigations slow down. That delay matters more when attackers can automate parts of the discovery and exploitation process.

Telegram Android Flaw Lets Attackers Run Code When Users Answer Voice Calls

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

A flaw in Telegram for Android could be chained with two other bugs to take full control of a victim's phone through a voice call, once the victim answered, according to security startup NebuSec.

The attacker needed only an ordinary Telegram account. Telegram fixed the flaw in version 12.10.4 of the app, released in late September, and NebuSec disclosed it on October 29.

Combined with an information-leak bug, the flaw gives the attacker an escape from the Telegram app to Android, NebuSec co-founder and chief executive Eten Zou told The Hacker News. Adding an Android root exploit then gives full control of the phone, including its messages, microphone and camera.

The flaw can be triggered in every version from 8.6.2 through 12.10.3, Zou said. Those versions came out between March 2022 and September 2026.

The company confirmed it in private voice calls on ARM64-based phones and has no evidence so far that it directly affects Telegram's iOS and desktop apps or group calls.

Anyone using Telegram for Android should make sure the app is on version 12.10.4 or later. The version number appears at the bottom of the app's Settings page. The flaw had no CVE identifier as of October 29.

The attack needs the victim to be called and to answer, Zou said, so setting Telegram's call privacy option to "Nobody" blocks it, and so does declining the call.

NebuSec has not seen the flaw used in real attacks, and believes no one else had realized it could be turned into remote code execution.

NebuSec reported the flaw to Telegram on September 26, after version 12.10.4 had shipped. Telegram acknowledged the report but did not believe the flaw could be turned into remote code execution, so no CVE was assigned and no bug bounty was paid, Zou said. The Hacker News has asked Telegram for comment.

During a Telegram call, the two apps send each other short messages to set up the call and report its state. One type, called MediaState, reports whether the microphone is muted, whether the camera is on, and how the video is rotated.

The flaw was in the code that reads MediaState messages. That code did not handle missing fields correctly and accessed memory it should not, according to NebuSec.

Telegram's published source code for version 12.10.3 contains a flaw that matches that description, a review by The Hacker News found. When a MediaState message included a rotation value, the code checked that value. It then read a different field, the video state, even if the message had no such field.

Version 12.10.4 reads the rotation value from the right field. The calling code that uses this message was switched on in version 8.6.2, the first version NebuSec names.

Telegram's Android, iOS, and desktop apps use one shared library, called tgcalls, for calls. A change labeled "Fix camera rotation" made the same correction in tgcalls on April 21, 2026.

Telegram's iOS source code included that change from version 12.7, released in May, and the desktop app's code from version 7.0.1, released in July. Telegram for Android received it in version 12.10.4 in September.

Whether the earlier code could be exploited in those apps has not been shown.

NebuSec's video shows two phones, one marked as the attacker and one as the victim. The victim accepts a Telegram call. About half a minute into the call, the victim's phone switches to its home screen, the app icons fall down the screen, and a "HACKED BY NEBUSEC" logo appears.

The video does not show which Telegram or Android version the victim's phone was running. No technical write-up of the flaw was on NebuSec's website as of October 29, so the attack chain, including the two other bugs, depends on the video and on what the company says.

NebuSec, a startup backed by Y Combinator, says its Code Security product, which runs on OpenAI's GPT-5.4 model, found the flaw. In July, the company described an Android exploit chain that started with a Firefox flaw and reached the kernel of an ARM64 device running Android 17.

Separately, the Zero Day Initiative (ZDI) published an advisory on October 15 about an unpatched flaw in rlottie, the library Telegram apps have used to draw animated stickers. The flaw, tracked as CVE-2026-111105 (CVSS score: 7.0), can let an attacker run code if a user opens a malicious file or page, ZDI said.

Telegram had told ZDI in March that checks on its servers mitigated the flaw, and in April asked ZDI for a full remote code execution chain.

Those checks could be bypassed, researcher Saifeldeen Aziz says in the abstract for his OffensiveCon talk in Tokyo. The research used AI-guided fuzzing, which feeds code with large amounts of broken or unexpected input, to find memory-corruption bugs in rlottie across Telegram's iOS, Android, and desktop apps. It then chained those bugs with flaws in how stickers are delivered and checked to run code on Telegram for iOS.

The Android app replaced rlottie with tlottie, a library written in Rust, between versions 12.8.1 in June and 12.10.0 in August, according to Telegram's published source code. The desktop app's code made the same switch in September, and the iOS code added tlottie in version 13.0 in October while still including rlottie.

The Rise of the Threat Operator: How AI Will Redefine Security Operations and Careers

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

AI is beginning to take over much of the work that has traditionally defined the security analyst's job. Investigating alerts, collecting evidence, correlating activity across tools, and executing response actions are becoming tasks that AI systems can perform on their own. As these capabilities mature, security operations centers (SOCs) will see major changes in how work is organized, how decisions are made, and what is expected of the people responsible for defending organizations.

For security professionals, this is a chance to take on a much broader role. As AI assumes more of the operational workload, analysts can move beyond individual alerts and investigations to direct the defense across the entire security lifecycle. We call this emerging role the Threat Operator: an AI-native security professional who translates business risk into defensive priorities, directs AI-driven operations, and exercises judgment over the decisions and actions taken by those systems.

The impact reaches beyond day-to-day SOC work. It will change the skills organizations need, how security professionals develop expertise, and the career paths open to people entering the field.

The traditional SOC developed around specialized functions, each supported by its own tools and workflows. Threat intelligence teams study adversaries, detection engineers create rules, threat hunters search for activity that existing controls may have missed, analysts investigate alerts, and incident responders contain confirmed threats. These functions are closely related, yet the work often moves between teams through separate systems, tickets, and manual handoffs. AI is starting to tie these activities together. For example, intelligence about a new threat can lead to a hunting hypothesis, which can reveal a detection gap and produce a new detection. That detection may identify suspicious activity requiring investigation, followed by containment and further improvements to the organization's defenses. AI agents can coordinate and execute these workflows, carrying context and findings from one stage to the next.

That changes where security professionals add the most value. A Threat Operator works across the defensive lifecycle, setting priorities based on the organization's exposure, business operations, and threat landscape. They determine which risks deserve attention, what the defense should accomplish, how much autonomy AI should have, and when a decision requires human intervention. They are also responsible for judging whether the operation is actually improving security.

Consider a financial institution facing a newly identified threat targeting identity infrastructure. AI agents could assess the institution's exposure, hunt for relevant activity, identify gaps in existing detections, and recommend defensive actions. The Threat Operator would provide the institutional context needed to guide that work, including which systems support critical business processes, what constitutes unacceptable risk, and which actions require authorization.

The result is a gradual shift from human-in-the-loop to human-on-the-loop, with security professionals supervising and governing AI-driven operations. The level of autonomy will depend on the maturity of the technology, the consequences of particular actions, and the organization's tolerance for risk, but a human remains accountable throughout.

Junior security analysts will feel some of the biggest effects. For decades, the SOC has provided an entry point into cybersecurity, with analysts developing their skills through alert triage, evidence collection, investigations, documentation, and escalation. Although much of this work is repetitive, it has also served as an apprenticeship. Over time, analysts learn how systems behave, how attackers operate, and how experienced practitioners distinguish genuine threats from benign activity. As AI absorbs more of these responsibilities, organizations will need to rethink how that experience is acquired. The traditional progression from handling simple alerts to managing complex investigations may become less relevant as AI takes on more sophisticated work. Without a deliberate approach to training, security teams may struggle to develop the experienced professionals they will need in the future.

AI can also open up a different path for professional development. Junior Threat Operators can gain supervised exposure to a much wider range of security activities, examining how intelligence informs hunting, how detections are developed, how investigations reach conclusions, and how response decisions affect the business. They can review the evidence behind AI-generated findings, challenge assumptions, identify missing context, and learn from the decisions made by more experienced colleagues. This only works if organizations invest in technical fundamentals and structured mentorship. Analysts still need to understand networks, operating systems, attacker techniques, and the security technologies underlying AI-driven workflows. Experienced practitioners will need to teach younger colleagues how to evaluate conclusions, recognize uncertainty, and exercise judgment when the available evidence is incomplete.

For the current generation of security analysts, technical proficiency has often been measured through familiarity with security tools and the ability to extract useful information from them. Query languages, detection logic, endpoint telemetry, and investigation techniques have been central to the profession. Those skills still matter. AI adds new demands on top of them: orchestration, governance, and interpreting automated decisions.

Threat Operators will need to translate business security risks into clear defensive objectives that AI systems can execute. They must understand the organization's architecture, critical assets, operational dependencies, and relevant adversaries, and know how to communicate that context to AI agents. Their work will involve evaluating hypotheses, validating evidence, setting escalation criteria, and determining whether an automated action has achieved its intended outcome.

For example, an AI system investigating a compromised server may recommend immediate isolation. That call could be technically sound. But the server may support a critical business process where disruption carries significant consequences. A Threat Operator must understand those dependencies and determine how the response should proceed, balancing containment requirements with operational risk. This need for defined oversight and accountability is also reflected in the NIST AI Risk Management Framework.

The Threat Operator role should become a career path with increasing levels of responsibility. Early-career operators can focus on validating evidence, reviewing AI conclusions, adding environmental context, and understanding how decisions connect across the defensive lifecycle. As they gain experience, they can begin translating business risks into defensive objectives, directing agent workflows, identifying coverage gaps, and determining when operations should escalate or act.

Senior Threat Operators will take responsibility for defining autonomy boundaries, governing consequential actions, evaluating the reliability of AI-driven decisions, and measuring whether security operations are reducing organizational risk. Professionals may enter this career path from investigations, threat intelligence, detection engineering, incident response, security architecture, or risk management, bringing different areas of expertise to a role that spans the entire defensive operation.

Security leaders should start building the training, governance, and progression frameworks needed to support these responsibilities. That includes establishing which decisions require human approval, how operators validate AI-generated evidence, how autonomy expands as systems demonstrate reliability, and how individual performance is evaluated. Measures such as the quality of defensive decisions, the closure of detection gaps, and improvements in threat coverage will matter more alongside traditional operational metrics.

This will happen at different speeds in different organizations. Security professionals will have more say in how their organizations defend themselves. The old SOC trained people to operate tools. The AI-native SOC has to train them to operate the defense.

26,400 Valid Cloud and AI Credentials Found Exposed in Public Gitee Repositories

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

26,400 credentials that developers left in public code on Gitee, a Chinese code-hosting service, still worked when a researcher tested them. Anyone who copied one from that code could have used it.

Independent researcher Ben Zimmermann found them by scanning 7.25 million public Gitee repositories and reported the results on October 28. Most were keys for cloud and AI services, led by 9,473 Alibaba Cloud AccessKey pairs.

Zimmermann sent the vendors with the most exposed keys a list of their credentials, but he did not contact the developers who leaked them. When he published, he had not confirmed that any of the reported credentials had been revoked. So anyone who has pushed a key to a public Gitee repository cannot assume it has been revoked.

The scan ran for about a month, but Zimmermann did not provide the dates, so it is unclear how long ago the credentials were tested. He also did not say whether anyone else had used them.

He ran two secret scanners, TruffleHog and Kingfisher, over every repository. Both tried each credential against the service that issued it and kept only those that worked, he wrote.

The scanners read each repository's full commit history. A key that a developer later removed from the code could still be found and counted there.

The 26,400 figure counts each credential once, regardless of how many repositories it appeared in. By commit date, 12,242 of the credentials came from 2025, nearly half the total. Some dated to the late 2000s.

After the Alibaba Cloud keys, the largest groups were 3,805 YouTube API keys, 3,170 DeepSeek keys, 1,489 keys for Zhipu's BigModel AI platform, and 1,348 OpenAI keys. Smaller numbers were found for GitHub, AWS, Google Cloud and Google's Gemini.

One of the credentials was "an active organization-admin credential for a major enterprise AI platform," Zimmermann wrote. He did not name the platform or say what the credential could reach.

What a working key lets someone do depends on the service. OpenAI says that a compromised key allows another person to use the account's quota without the owner's consent. That can cause "data loss, unexpected charges," a used-up monthly quota, and interrupted API access.

A YouTube API key is a Google Cloud API key that identifies a project, Google says. Without API restrictions, such a key can be used with every API that accepts Google Cloud keys.

Treat any key that has ever been in a public Gitee repository as exposed, and revoke it at the provider. Deleting a key from the code or rewriting the repository's history does not revoke it, as noted by TruffleHog's maker, Truffle Security.

MongoDB makes Kingfisher, and Zimmermann's post was developed with its Kingfisher team.

In this scan, TruffleHog found 12,737 credentials that worked, and Kingfisher found 14,664, but only 1,001 were found by both. Each tool alone found about half of the total.

TruffleHog found almost all of the Alibaba Cloud keys. Kingfisher found all 1,489 BigModel keys, because TruffleHog has no detector for Zhipu's keys, Zimmermann wrote.

Teams that rely on a single scanner should verify its detectors against the services they use.

China's Ministry of Industry and Information Technology chose Gitee in 2020 as the base for a national open-source code-hosting platform.

Gitee's public API is limited, and a 2021 attempt to study leaked credentials on the site gave up because of it.

Gitee's rate, 3.64 working credentials per 1,000 repositories scanned, is higher than the rates from earlier scans of GitLab (3.11) and Bitbucket (2.39). Those scans used only TruffleHog, Zimmermann wrote.

Based on TruffleHog's results alone, Gitee's rate is 1.76, but that count excludes services TruffleHog does not cover, such as Zhipu. So neither figure shows which platform leaks more.

An AI Breakthrough Has Made Decades of Computer Science Research ‘Irrelevant’

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Linköping University professor Peter Jonsson is set to have his work presented in two weeks’ time at one of the most prestigious conferences in theoretical computer science. As of Monday, much of that work is “dead,” he says, after AI showed that a 27-year-old hypothesis underpinning it is wrong.

Both OpenAI and Anthropic claimed this week to have disproved the exponential time hypothesis (ETH). Vast swaths of theoretical computer science research on complexity and algorithm design have been built on the premise that the effort it takes to solve certain problems increases exponentially with the size of the problem.

Jonsson expects his predicament will be “very common” at the IEEE Symposium on Foundations of Computer Science, where his work will be presented by one of his coauthors. “People will start the talks: ‘ETH is false, half of my paper does not work,’” he says. It’s a vexing problem, Jonsson says, “but at the same time, we learn a lot from it. And this is what science is about.”

Researchers haven’t independently verified, let alone had time to fully understand, the AI-produced proofs, which both firms have published on GitHub in both natural language and its machine-checkable Lean format. OpenAI has asked the UC Santa Barbara computer scientists who originally proposed the hypothesis, plus an MIT academic who has refuted a version of ETH, to rally researchers to unpack the proofs. So far, this effort includes a Google form asking for volunteers and feedback, and a commitment from OpenAI to fund a conference on the topic.

UC Santa Barbara professor Daniel Lokshtanov plans to join the effort, as he estimates the result—if confirmed—will render him “galactically wrong” and make around 50 of his published papers either “pointless” or in need of a revisit.

“It’s just a giant bomb dropped into the middle of the field,” he says. “It’s really cool and terrible at the same time.”

Thore Husfeldt, head of the algorithms research group at the IT University of Copenhagen, had spent most of this year thinking about one single problem in his subfield. “As far as I can tell, it’s now all irrelevant,” he tells WIRED. Having first formulated a version of the hypothesis now disproved by OpenAI, he has been writing calculations on his blackboard to figure out what other parts of his work might have become obsolete due to the “once-in-a-generation result.” Unlike the ennui that has gripped math researchers who have faced similarly field-upending proofs generated by AI models, though, Husfeldt expressed enthusiasm about the new results.

The finding is “fantastic,” he says. “Being a mathematician is a lot like stumbling about in a completely dark room,” he explains. “It's like somebody just illuminated an entire subfield in floodlights of knowledge, and now we just run around like overexcited bunnies and look at all the nooks and crannies that we can suddenly explore. So it’s a super exciting time.”

For centuries, science has advanced through making hypotheses and proving them wrong. It also isn’t unusual for an academic to be scooped or have their work otherwise undercut by another research group. But AI has accelerated this, obliterating whole research programs and spooking researchers in specific fields of math and science who wonder where they stand now that machines can outperform them.

“The last few months have been really tough. It's a lot of doom and gloom, because every week, or every second week, the results announced by AI just annihilate the ongoing research projects of many people,” Husfeldt says. “That is psychologically taxing for many people,” he says, adding that his department has considered hiring an occupational psychologist because “some people are really depressed and really sad.”

Researchers have also been overwhelmed by the volume of content now being produced, thanks to AI, including slop-level results. Midway through the interview, Husfeldt receives what he suspects to be an AI-generated 17-page paper on the consequences of the ETH result from a random Gmail account. He won’t read it: “Reading math is a very big investment of cognitive time,” he says.

OpenAI has directly contributed to this; earlier this month, it dumped 722 manuscripts on 400 problems on GitHub, to the annoyance of academics, who complain this makes it difficult to digest the results. Adding to the frustration were several documents that contained errors, reflecting what some mathematicians saw as a hasty rollout designed to juice the company’s planned initial public offering rather than moving the field forward. This time around, OpenAI’s 60-odd-page paper on ETH seems to be written better than the companies’ past publications, academics tell WIRED.

They are now scrambling to unpack the paper and find what other results they can quickly deduce from it.

If ETH is false and it doesn’t, in fact, take exponentially more time to solve problems as they become more complex, that’s “exciting,” says Victor Lagerkvist, an associate professor at Linköping. He plans to return to problems he had previously given up on under the assumption ETH was accurate.

OpenAI’s finding could also have impacts on the cryptography that underpins web security, which is based on the assumption that certain mathematical problems take an impractically long time to solve. While this particular result doesn’t directly affect cryptography, “it should definitely scare some cryptosystem designers,” says Lokshtanov.

That’s why continued human and AI-assisted work in theoretical computer science is important, Husfeldt adds: “We want the open scientific process to identify our misunderstandings about computation, in particular because lots of modern digital infrastructure is built on assumptions about computation.”

As for Linköping’s Jonsson, he plans to revisit both his own and others’ papers that hinge on ETH being true, and believes his conference paper may eventually be salvageable through another method. He’s excited to look into the details of OpenAI’s proof and see what he can learn from it and apply it to new problems. Even though it undoes the assumptions underpinning his work, having a verdict for ETH is something he could only “dream of” before, he says. “These are exciting times,” he adds. “Most people would never experience anything like this in their career.”

“I don’t care if it's a human-written proof, or it's written by AI, or if an alien transmitted this proof to us. If it’s true, then we must simply use it in the future.’’

Cisco Patches Actively Exploited ASA and FTD VPN Flaw That Can Crash Firewalls

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Cisco has released patches to address a high-severity security flaw in Secure Firewall Adaptive Security Appliance (ASA) Software and Secure Firewall Threat Defense (FTD) Software that it said has been exploited in the wild.

The vulnerability, tracked as CVE-2026-76418, is rated 8.6 on the CVSS scoring system. Successful exploitation could allow an unauthenticated, remote attacker to cause the device to reload unexpectedly, resulting in a denial-of-service (DoS) condition.

According to Cisco, the issue is rooted in the Remote Access SSL VPN service of ASA and FTD software.

"This vulnerability is due to logic errors when secondary authentication is configured on a tunnel group," it said in a Wednesday advisory. "An attacker could exploit this vulnerability by sending a crafted request when connecting to the SSL remote access VPN. A successful exploit could allow the attacker to cause the affected device to reload, resulting in a DoS condition."

The network equipment major said it became aware of active exploitation of this vulnerability in October 2026, but did not share any specifics as to when the attacks began, who is behind them, and the scale of the efforts.

"UAT-11473 then installed a custom malware framework we track as 'KeyDrift' consisting of multiple components [like PolyFlame and LittleFilch] geared towards collecting sensitive keying information, acting as backdoors and intermediate command-and-control (C2) hosts," Cisco Talos said.

"The framework is designed to provide long-term persistent access and automated exfiltration of sensitive keying material. A Hacker Targeted High-Stakes Poker Players With Malware That Exposed Their Cards

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

In a fitting sign of the times, the hacker’s carefully laid plans were foiled by an AI agent.

It was September 25, 2026, and Alex, a professional online poker player, was using his Claude AI agent to review some play statistics. (Alex only agreed to speak with WIRED under a pseudonym to avoid any risk of reprisals from threat actors.) After Alex’s SQL database crashed and needed to be reset, the Claude agent noticed something suspicious: A program called MeshAgent was operating in the background, where it seemed to be capable of capturing Alex’s screen and even controlling his entire machine.

Thanks to the Claude agent’s report, Alex could see the program had been installed on April 24, and not by Alex himself. Alex says the agent identified 11 time-stamped events when the program had been capturing his screen based on graphic errors it caused during screen sharing instances. During all 11, Alex had been playing a session on ACR, also called Americas Cardroom, a major worldwide online poker operator.

He checked his hand histories and quickly found the most troubling info yet: The same opponent, playing under the handle OxOO, was at his table for 10 of those 11 sessions.

The handle was familiar. Alex and several friends in the high-stakes community had shared suspicions about this player’s behavior in the past. Alex checked the player’s win rate stats via a public tracking site; they were astronomically higher than the best players in the world, a statistical impossibility given the sample of hands played. In Alex’s view, it was glaringly obvious that this player was cheating.

An investigation by Alex and other members of the high-stakes community in subsequent days confirmed his fears—and then some. Alex was one of hundreds of players allegedly targeted with this type of malware by the same reported threat actor across a period of multiple years. Alex, who was the first to discover MeshAgent on his computer, claims he was “only” ripped off for around $30,000, a relatively moderate sum for the level he plays at; many of his peers weren’t so lucky.

With millions of dollars allegedly stolen across the biggest sites on the internet, the poker world is searching for answers about how the scheme was allowed to continue so long, whether major sites took the risk seriously after it was reported, and whether online poker itself has been irreversibly compromised.

Poker has never been short on cheating controversies; online poker especially so. The “superuser” method, in which a cheater gains unauthorized access to their opponents’ cards and can therefore act with perfect information against them, was one of the first to show up online.

Two major sites in online poker’s early days, Absolute Poker and Ultimate Bet, served as cautionary tales in the mid-2000s. In separate instances, superuser cheaters were able to gain insider access to the websites and bilk players for millions of dollars. (Much of the loot was refunded to players following an investigation.) Those high-profile incidents led to tightened security measures from many top poker sites.

Another minor superuser incident took place in 2013, when a Finnish high-stakes player said his laptop had been stolen from his hotel room during a European Poker Tour tournament in Barcelona. When the laptop was recovered, it had been infected with malware that allowed a hacker to view his screen remotely. And maybe the most famous superuser scandal of all took place on the live felt: In a story that made it all the way to SportsCenter, a player named Mike Postle was accused of stealing over $250,000 from livestreamed games at Stones Gambling Hall in 2018 and 2019 with the aid of what observers believed to be an alleged accomplice with access to live card data who fed information to Postle’s phone. (Postle denied the accusations, alleging it was “fake news.”)

Outside one relatively small (and quickly remedied) incident in 2023, though, the online poker world had gone years without a confirmed superuser incident—until now. And some of what’s known about this latest attempt signals a savvier threat actor than in previous scandals, plus a degree of patience not typically seen in attacks like these.

“Traditionally, when you see these types of financially motivated threat actors, they will get access to a system and then as soon as they’re on it, they’ll do a scope of what they have access to and then they’ll hit everyone all at once and dump all the wallets,” says WolfSec, a cybersecurity professional who consults with many high-stakes poker players on security measures. He was first to break the news of the MeshAgent scam on September 29, on his X account. (WolfSec agreed to speak to WIRED under the condition his real name not be used out of fears of reprisals from hackers; WIRED independently confirmed his credentials as a cybersecurity expert.)

But this hacker didn’t do any of that, despite many of these players having large cryptocurrency holdings and other investments accessible on their machines. The attacker seemed instead to be performing advanced reconnaissance. In fact, WolfSec believes the same threat actor was attempting to attack players’ machines as early as 2022 using a more basic technique; because no known funds were stolen at the time, no other action was taken once the players wiped the malware from their computers.

It appears, though, that the hacker was simply biding his time and improving his methods in preparation for an eventual strike.

Instead of targeting individual players directly, this more recent attack involved third-party software programs called IntuitiveTables and Jurojin. These programs allow professionals to play dozens of online poker hands at once. Using these popular “multi-table” tools, players can switch between live games with a keystroke, place bets or make plays with hot keys, and other actions that make it easier to play at several virtual tables at the same time. The hacker compromised both applications, WolfSec says, pushing malicious software to over a thousand estimated users.

In the case of Jurojin, the attacker gained access to the developer’s own system for software updates and was able to deliver the remote-access agent to existing users through normal, automatic updates.

The developer of Intuitive Tables was running Jurojin on their test computer, and that machine got the remote-access agent as part of Jurojin’s compromised software update. Using the agent, the attacker added malicious code to the Intuitive Tables application before the developer signed the security certificate for an updated build of the app. That version carrying the malicious code was posted to the Intuitive Tables website as a public download, and everyone who installed that version of the app unknowingly also installed a backdoor on their computer.

In both instances, the malicious code was delivered through a standard update channel or an official release, so neither the users nor their antivirus apps detected anything amiss.

The modified version of Intuitive Tables behaved exactly like the clean version, with one exception: It also checked players’ files for their usernames.

“If you were on a hard-coded list that was stored on the attacker’s infrastructure, which [the malware] reached out to and downloaded and compared your username to, then it acted as a malicious program and downloaded additional malicious files,” WolfSec says. “If you weren’t on that list, then it became the normal program and didn’t do anything malicious at all.”

The list appears to have been populated primarily with regular high-stakes players across several sites. All of the players on the list appear to have had the MeshAgent program installed covertly on their machines. The hacker was ready to pounce.

In early 2025, a couple of new players began frequenting high-stakes games—one on ACR (using the handle “JackKlompus”) and another major global site called CoinPoker (handle: “Europe”). Strangely, despite not being familiar to other regulars in these games, the players refused to identify themselves in table chats, a common request that’s typically granted by new players in high-stakes poker. The new opponents were also winning with improbable frequency. (Later, once the pros started sharing information about their games, it was pieced together that these players were the same person.)

Mike, a professional poker player who spoke to WIRED using a pseudonym due to fear of reprisals from hackers, played on both sites at the time and was at tables with the player using these handles. Mike says at first he wondered if the mystery player’s success was somehow explainable. Maybe they were doing something new that Mike and his fellow pros just hadn’t figured out.

“You could kind of excuse it” at first, Mike says. “Maybe this guy is really, really good or something.”

As the number of winning hands grew, though, Mike and several high-stakes friends became more suspicious. They initially suspected that the player was using real-time assistance via game-theory-based engines that outperform the best human players. Real-time assistance is banned across major sites, but is difficult to police perfectly and is something pros are regularly watching out for. Mike mostly stopped playing at tables with the mystery player, as a precaution.

Like WolfSec, Mike reflects on a relative level of skill and discipline employed by this player during those 2025 sessions, especially compared to other known cheaters in poker history. The account generally used standard bet sizes and played normal hand ranges. Its session-by-session play never raised too many eyebrows; only the account’s win rate over time drew scrutiny.

But in June 2026, Mike played a two-hour heads-up (one-on-one) session on a different site, ClubWPT Gold, which he’d later determine—following reviews with the website’s security team—came against the same player from the 2025 sessions. The player used a different handle to evade detection, so Mike didn’t see a reason to be extra cautious. The opponent simply steamrolled Mike, making every correct decision even in seemingly impossible spots—almost like he could see Mike’s cards. “It was very blatant,” Mike says.

Immediately after the session, Mike messaged several friends in the high-stakes world to say he thought he’d been cheated.

Turns out he was right. When word of the hack broke publicly on WolfSec’s X account, ClubWPT Gold investigated. The site banned the account Mike had played against and refunded him for his losses, says Randy Lundy, head of customer operations for ClubWPT Gold.

This alleged cheater’s presence in online circles was an open secret across the community by this point. In fact, Mario Mosböck, a poker ambassador for CoinPoker who was authorized to speak about the company’s response to the hack, says the site began investigating this player as early as 2025, banning them and refunding over $100,000 in allegedly stolen funds to affected players. (Mosböck says the return of funds was delayed several months because the alleged cheater appealed the confiscation to regulators.) The player’s simple win rate and play style statistics appeared to be evidence of malfeasance, even if the site couldn’t definitively determine how the cheating was happening.

How, then, was the same alleged cheater allowed to keep ripping off players like Alex and Mike on multiple other supposedly reputable sites more than a year later?

“They confirmed multiple times that they looked at my report, but for whatever reason they didn't act on it,” says Patrick Howard, a professional poker player and founder of the coaching company Mobius Poker.

The “they” he’s referring to is GGPoker, arguably the most well-known site in the world for non-US players. Howard says he submitted a report to the site in early September 2026, weeks before the MeshAgent hack became public, highlighting the alleged cheater’s unusual play and urging the site to investigate.

“I found multiple three- to four-standard-deviation outliers,” Howard says, and that was across a limited hand history sample sent to him by friends and clients. He sent his findings to the GGPoker team but received no response. He got a reply only after WolfSec’s public reveal of the hack on X, with the site telling him there “wasn’t conclusive evidence” to act at the time of his complaint.

Various online poker sites handled the incident differently. Players have largely praised CoinPoker for proactively banning the player based on win rate and play tendencies alone, which are accepted as definitive indicators of cheating at stakes this high and with samples this large; while ClubWPT Gold only seems to have been impacted later in the scheme, that site also appears to have acted decisively upon discovering it.

But the hacker remained active on GGPoker and ACR until late September, allegedly stealing between $1.5 million and $4 million, based on the estimates of the sources WIRED spoke to for this story.

“Players are frustrated, because they had been reporting this for a year,” says John Andress, head of game integrity for A5 Labs, a cybersecurity platform that provides anti-cheating services to ClubWPT Gold and other brands. “A few of the platforms just completely ignored them.”

This was despite signs that many feel were all too obvious.

CoinPoker says the player’s alleged true identity was known early in this process, after the company conducted a webcam security interview with them in February 2025. The name the player gave matched the handle the player later used on GGPoker, which requires players to use their real name as their handle instead of a pseudonym for certain high-stakes games. (WIRED is not naming the player because they have not been charged with any crime. The player did not respond to multiple requests for comment on this story). The CoinPoker spokesman says their team reached out to ACR with their findings as well and received no response. (Requests for comment from WIRED to ACR and GGPoker received no reply.)

To its credit, GGPoker acknowledged the incident and announced several fixes in an October 15 blog post, including banning third-party tools and adding win-rate anomaly detection. The site also says it traced the accused attacker’s funds to a Coinbase account and has asked the crypto company to restrict the account and preserve its records; it says it also provided the wallet addresses to industry watchdogs and law enforcement.

But ACR is going the opposite direction: On October 18, it emailed players claiming its security team found no compromised game outcomes or wrongdoing and will not issue any refunds—despite, in the same email, announcing a new feature to stop remote-viewing tools from capturing the images of the cards in players’ hands.

Other entities have taken concrete action: Both Jurojin and IntuitiveTables (via its Discord channel) released tools to help users detect whether the MeshAgent hack had affected their machines. AceGuardian, a research group that’s part of A5 Labs, put out an open-source “superuser detection” tool designed for use on any poker site. WolfSec says he submitted a complaint to the the Internet Crime Complaint Center, the cybercrime arm of the FBI, and has been working with players on improving machine security. The FBI, when reached for comment by WIRED, would not confirm receipt nor any details of this complaint.

But these efforts will be so successful only if the sites treat these incidents with more scrutiny and don’t just spring into action in the aftermath of major attacks.

“Ultimately, the sites have to ban the players,” Howard says. “I think they dropped the ball here.”

We urgently need to monitor AI agents’ actions in real time

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Right now, we’re effectively flying blind when deploying these tools. Here’s what we need to do instead.

This summer, hundreds of OpenAI agents tried to cheat on a cybersecurity test. They broke out of their test environment and successfully hacked Hugging Face, a site that they believed held clues about how they’d be graded. Around the same time, another OpenAI agent accessed private files from an Australian government website. It’s a problem that’s by no means confined to OpenAI. In the months since, Anthropic, Google, and Meta have also disclosed incidents in which their agents have gone off track. And worryingly, in many cases the agents eluded the very researchers and safety teams tasked with monitoring them.

AI agents are taking unauthorized actions, and the companies building and running them are mostly relying on luck and hindsight to mitigate any harmful impacts. They must do more to ensure safety. That’s why EU regulators and US agencies are rightfully calling for agent developers and deployers to monitor agents in real time. But these rules assume that companies can see what their agents are doing and why—when in reality, they lack sufficient visibility.

As agents roll out across critical sectors, from finance to government to medicine, we must be able to monitor them in real time to prevent wide-ranging and potentially devastating consequences.  And while safety depends on monitoring, monitoring requires observability: the capacity to capture what the system did, process it into signals, and present those to humans or automated oversight systems. In other words, we need to know what the agent did and why it did it. And as our recent research shows, current agent frameworks—the software that runs agents— do not reliably generate the crucial observability records we need to ensure that agents are deployed safely.

Agents present new kinds of problems that generative AI alone does not. They inherit the unpredictability of the LLMs they are built on, but where a generative AI system produces a single output for a human to act on, an agent performs longer tasks—it plans, picks tools, spawns sub-agents, and takes actions. So an agent’s course can take shape in a multitude of different ways, and no tests before launch can fully anticipate the risks. This makes observing the agents while they work even more challenging, and even more important.

With colleagues from academia, civil society, and industry, we studied the four most widely used agent frameworks to see what signals they actually emit. We found major gaps that made it hard to achieve key safety goals, like noticing policy violations, unauthorized actions, and even human oversight failures. Key observability requirements were missing—like Agent IDs that persist over time, and records about which humans approved agent tasks. This made it hard to tell which agents did what or assess whether they were taking unauthorized actions.

The good news is that these gaps, once identified, can be closed. Doing so starts with capturing two types of records: those that reveal what happened in an agent’s run and how the agent made its decisions. The “what happened” records identify the agent (while preserving privacy) and log how humans intervened and whether agent permissions or “memory” shifted, while the “decision” records show an agent’s reasoning and levels of confidence in the actions it’s taken.

Take, for example, agents working to process a bank’s mortgage loans. The system examines an application and recommends denying it, and then a human loan officer signs off on the decision. In a later audit, or perhaps even in real time, a bank or regulator needs to be able to reconstruct which agent made the call, which officer approved it, and how long they took. And the bank must also analyze records of how the agent arrived at its refusal decision in order to ensure it did not use off-limits information, like details about the neighborhood the applicant is from.

Recording “what happened” and “how the agent decided” require different approaches, but both are feasible. The current lack of “what happened” records is mostly a software plumbing problem that can be addressed through OpenTelemetry, an open observability standard maintained by engineers across the industry and by the agent frameworks adopting it.

OpenTelemetry has launched a working group drafting shared formats for tracing agents, but they have yet to be finalized. The group should urgently incorporate standards for maintaining persistent agent identity and for recording human interventions and changes to agents’ permission or memory. And it should be done before these systems can scale, all the while attending to the privacy implications of agent ID that links to real people.

Preserving “how agents decided” records is more challenging. The issue raises open research questions for model providers and researchers: Does the step-by-step reasoning a model displays, known as chain of thought, reflect how the model actually made a decision? And do we have reliable ways to measure how confident the agent is in that decision? These questions need answers before anyone sets standards for how such observability records are used.

No single organization or sector can close the observability gaps on their own, but together, they can support the infrastructure required to prevent dangerous incidents and support safety.

AI developers building agent frameworks, like OpenAI, Anthropic, CrewAI, and LangChain, must integrate telemetry signals recording an agent’s persistent identity, any human interventions, and any changes to an agent’s permissions and memory. Meanwhile, enterprises adopting these agent frameworks have an influential role to play; enterprises in regulated industries, like banks and hospitals, can put pressure on the agent developers to supply these missing observability records where standards do not yet exist.

Enterprises must also define policies, permissions, and roles that set out what agents can safely do, since telemetry alone cannot assess whether agents broke specific rules. Finally, regulators and AI standards institutes must specify the observability records required for high-stakes AI deployments while leaving the technical details to industry. We have already seen initial momentum here: NIST’s agent standards initiative in the US is working on agent identity, one of the most salient gaps we found in our research.

No bank would let a thousand unbadged employees loose on customer accounts and hope to piece together what happened when something goes wrong. Yet that’s how we’re deploying AI agents. Making their behavior observable is the first step toward fixing this. And by building the regulatory and policy ecosystem that makes it possible to act on what we see, we can hold organizations accountable. Until then, every task we hand to an agent hands over our agency, too.

A 2024 Aging Cell study likewise suggested that an aging clock shouldn’t be treated as a measure of someone’s overall biological age. “Ultimately, individual-level triggers precipitating death are inherently random and will never be truly forecastable,” Ludkovski says.

Death doesn’t work that way, she says, “so the measuring starts to serve a different need: the need to feel less afraid.”

Terry-Leonard is also the cofounder of the Center for Deeply Human Leadership, an independent research institute studying AI’s effect on brain health. She’s skeptical that consumer-facing longevity apps can lead to positive behavioral shifts on their own. “Facts don’t change minds,” she says. People understand that certain activities are unhealthy, but they do them anyway.

But even as I labored to improve my death date, the clock was always there, counting down. It was an albatross that moved in a single, uniform direction: tick, tick, tick. Time became a burden I was being forced to optimize.

It makes sense that people are preoccupied with the very thing they are trying to escape. The need for control is addictive. But instead of assuaging my anxieties and questions about the great beyond, Death Clock only seemed to amplify them.

As the image of the life I want to build sharpens in my mind, a life that has already unfolded in deliciously unforeseen ways, I realize it has less to do with how I will make things happen and has everything to do with who I want them to happen with. Life isn’t about adding more time, but making it count when we can. I silenced Death Clock’s notifications on my phone and texted a friend: “Let’s meet at 7.”

Liquid Glass Finally Makes Sense on the iPhone Duo

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Apple rarely admits a mistake. But when it unveiled new versions of its operating systems this summer, it came close.

“With all major design updates, there’s a natural process where we take a bold leap forward, and then we continue to iterate,” said Apple's human interface designer, Shubham Kedia, during a predictably sleek keynote video. “Our team really appreciates your feedback, and we considered it deeply as we refined the new design.”

Not quite “Sorry, everyone, we messed up,” but for Apple, practically an apology tour. The subject was Liquid Glass, Apple’s most divisive interface design since at least iOS 7. Apple's Vision Pro mixed-reality headset (which itself flopped) inspired the translucent design language, and the company brought it to millions of other Apple devices.

The result was a mess—at odds with Steve Jobs’ famous line, “Design is not just what it looks like and feels like. Design is how it works.” Liquid Glass started obsessed with gloss and effects, despite promises it would bring your content to the foreground. Yet Apple’s own press release showed interfaces with illegible text. Worse, users found constant reflections and flickering color shifts distracting, and a lack of clarity across devices hurt accessibility.

But iOS 27, alongside updates to Apple's other software platforms, signaled a shift in priorities after Kedia’s mea culpa. Kedia spoke of reincorporating design cornerstones in what was, if not quite a U-turn, then at least a rediscovery of a core principle: how it works. Instantly, interface elements across Apple devices gained greater clarity and structure, making it easier to tell apps' components from content. The most obvious change, though, was a slider.

Apple said it tuned Liquid Glass to diffuse complex content more effectively, keeping elements legible when above imagery and text. But it also acknowledged that not everyone wants the same thing—some users might prefer a more tinted look, and others “would like Liquid Glass to be even more clear.” You can now decide for yourself with the Liquid Design slider in Settings. For a company known for being opinionated, such bet-hedging was surprising but not unwelcome. Choice isn’t a bad thing, and now users had more of it.

“I immediately pushed that slider all the way to the most tinted setting, and pretty much all the legibility issues vanished,” Ben Rice McCarthy, an indie developer behind popular apps like Obscura and Indigo, tells WIRED. McCarthy has long criticized Liquid Glass. Now? Not so much.

“Liquid Glass introduced a lot of issues without adequate solutions, but this year’s operating systems solved or improved a lot of them,” McCarthy says. “There’s the adaptiveness of the interface. Buttons can grow into menus. Controls merge and divide like cells as you transition between views. Toolbars can expand and contract smoothly as the view changes size.”

Flexibility matters when resizing windows across any device. But while announcing its updates, Apple also dropped major hints that all but confirmed new hardware—it showed iPhone apps running on an iPad or a Mac could resize to a suspiciously specific shape that matched the rumored inner display dimensions of Apple’s upcoming folding phone.

When Apple showed off the iPhone Duo, everything clicked. Its passport-shaped display bucks the trend of iPhones and their rivals growing taller over the years. The Duo is wider and almost squat, and when opened, it naturally defaults to landscape, echoing the iPad Mini display.

Apple being Apple, it wanted to avoid the jarring jolt between displays that’s often evident on rival foldables, so it made content appear to move seamlessly from one screen to the other. That begins with the hardware. As Molly Anderson, Apple's vice president of Industrial Design, said at the September keynote: “To achieve this continuity, we designed iPhone Duo around a consistent aspect ratio that is the same across both displays.” But it’s the software—rooted in Liquid Glass—that sells the illusion.

The most arresting element is a fancy animation, which various folks in the Android space are now busy being “inspired” by. It reinforces the idea of a flowing interface. Meanwhile, Liquid Glass freed Apple from being prescriptive about where essential controls live. On the Duo, they sit at the side. When the phone’s closed, that frees up space for content. When it’s open, the controls stay in a consistent spot, so you never have to hunt for them. Reorient the device, and everything settles into the most appropriate place.

That’s form following function, not function being subservient to form. This device and its flexible interface don’t strictly need the Liquid Glass design language, but the two feel made for each other. Liquid Glass finally makes sense on the iPhone Duo—and with Apple’s other refinements, it’s starting to make sense elsewhere, too.

How much of this is happenstance is hard to say. Given Apple’s lead times, pure coincidence seems unlikely. And even if Liquid Glass wasn’t made with the Duo in mind, it adapts to it.

Liquid Glass feels more considered. It’s increasingly tuned for individual devices rather than governed by a “universal” aesthetic forced onto them all. The result is operating systems that feel solid rather than fragile, with interfaces less likely to fight content for your attention. On Macs and iPads, the Liquid Glass revamp now looks more like a love letter to Aqua—Apple's water-themed interface introduced in 2000. On the iPhone, it’s usable again. On the Duo, it’s a delight.

That’s not to say it’s perfect. “There’s some weirdness that hasn’t been fully resolved, and there needs to be a consistency to all these materials or the metaphors break down,” McCarthy says. “But overall, Liquid Glass is vastly improved.”

And it’s worth remembering that while the Duo is new, Liquid Glass is relatively young, too. As developer Steve Troughton-Smith wrote, “For some iPhone apps, even with keen developers, it will take six months to a year of work to properly support iPhone Duo. A lot of developers are still trying to finish the Liquid Glass transition they started last year.”

A useful reminder that transitions take time. But at least now, Apple’s vision looks clear.

Attacker Tried to Exploit Alpine Linux’s GitLab via CVSS 10.0 Flaw Its Ruby Left Open

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

An attacker tried to exploit a critical GitLab vulnerability on the Alpine Linux project's own GitLab server a week after GitLab released a fix, Alpine Linux said on 28 October.

The flaw, CVE-2026-97229 (CVSS score: 10.0), can let an attacker run code on a GitLab server through a crafted regular expression in a CI configuration. Alpine found no evidence that the attack worked but cannot rule it out, so it rebuilt the server from scratch and reset every account's password.

GitLab's fix is a set of patches to the Ruby that GitLab ships in its own packages and container images. Alpine's GitLab image used standard Ruby, so upgrading the server to GitLab 19.3.6 on 22 October did not fix the flaw.

For anyone running GitLab on their own Ruby, built from source or in their own container image, "upgrading GitLab is not enough," Alpine said. Those servers also need Ruby 3.3.13, 3.4.12, 4.0.9 or later, and users of Alpine's alpinelinux/gitlab image need to pull 19.3.6 again.

The server gitlab.alpinelinux.org hosts aports, the repository from which Alpine's packages are built. Packages built from 20 to 24 October, and the 21 October releases, came from aports changes verified against records outside GitLab, according to Alpine.

Those releases include the minirootfs files that the official Alpine Docker images are built from. Alpine is extending the checks to 27 October, when it closed the server. The keys that sign its packages and releases have never been on the GitLab server.

On 13 October, Alpine upgraded the server to GitLab 19.3.4 instead of 19.3.5, which it calls a mistake. The server was still on that version, without the 12 October fix, when a newly registered account began probing it on 20 October.

The account sent crafted CI configurations to the server on 20 and 21 October. They crashed GitLab worker processes 8 times, and the main attack on 21 October also caused 502 errors and caused CI jobs to fail.

In 4 of those crashes, the attacker got partway through the exploit and failed at the next step, according to Alpine. The attacker also downloaded Alpine's GitLab container image, which Alpine said: "suggests they were tuning the exploit to our exact build."

Alpine blocked the account on 23 October. The attacker came back on 25 and 26 October and tried to get back in, but those attempts failed, Alpine said.

On 26 October, Alpine found that the server was still vulnerable after its 22 October upgrade to 19.3.6. The next day, it closed GitLab to everyone except its developers and build servers and started rebuilding it.

The rebuild finished on 28 October. Alpine also replaced GitLab's secret keys, and the rebuilt server runs Ruby 3.3.13 or later, which has the fix. Alpine is testing it before reopening it to the public.

Alpine found no sign that the attacker's code ran on the server. Timing probes showed no delays;; there were no unexpected files, keys, hooks, or processes; and no private data was sent back to the attacker via any web or API request that Alpine can see.

It cannot be sure, though. "A successful exploit would leave no crash and no trace in the web logs," Alpine said. Some logs from the attack day are gone, including background job logs and the old container's filesystem, and neither Alpine nor its hosting provider logged outbound network connections.

Because the evidence needed to confirm code execution no longer exists, Alpine treated the server as compromised and rebuilt it to remove any foothold a successful exploit could have left.

Beyond the password reset and the new secret keys, Alpine has not said whether runner tokens, CI/CD variables, access tokens or integration credentials stored on the server have been replaced.

To check its packages, Alpine confirmed that every aports change added from 20 to 22 October arrived through a recorded push by a known developer. It checked this against records it says the attacker could not reach: a developer's copy of the repository and all 45 build servers. Every package built from 20 to 24 October came from aports changes as published on git.alpinelinux.org.

GitLab compiles the regular expressions in CI configurations with Ruby, and the bug behind CVE-2026-97229 is in Onigmo, the regular expression engine built into Ruby.

GitLab's 12 October release fixed it by patching the Ruby inside GitLab's Linux package and container images. Ruby's own fixed versions came out on 22 and 23 October.

A GitLab upgrade does not change a server's own Ruby, so a GitLab install on standard Ruby keeps the flaw until Ruby itself is updated to a fixed version, as Alpine found.

GitLab's fixed Linux packages and its official container images carry the patched Ruby. A self-compiled install, or a container image that installs Ruby separately as Alpine's did, does not get it.

As of 29 October, neither of GitLab's patch release posts for 12 and 21 October tells administrators of self-compiled installs to update Ruby. GitLab's self-compiled installation guide still lists Ruby 3.2 as its minimum version, and Ruby 3.2 reached end of life in April and will get no fix.

GitLab's advisory says that, "under certain conditions," the flaw could have allowed an unauthenticated user to run code on the server. GitLab.com and GitLab Dedicated are already patched.

Astronomers Discover a Possible New Dwarf Planet in Our Solar System

📅 Oct 29, 2026  |  Category: Other  |  Read Source →

Scientists are on the verge of confirming the discovery of another member of the solar system, a potential dwarf planet. Astronomers at the Vera C. Rubin Observatory in Chile located the object, provisionally named 2026 ED138.

The prospective planet measures somewhere between 600 and 1,500 kilometers in diameter and is located about 46 astronomical units from the sun (an astronomical unit being Earth’s approximate distance from the sun). For comparison, Pluto—which is also now considered a dwarf planet—orbits at an average distance of 40 astronomical units. Based on its location, ED138 belongs to the population of trans-Neptunian objects. According to its discoverers, it could be one of the brightest known objects of this type and also among the largest.

Like Pluto, the possible Dwarf planet’s orbit is tilted relative to the plane on which the planets orbit.

The difference between a planet and a dwarf planet is largely their environment. While both orbit the sun and have sufficient gravity to assume a nearly spherical shape, a planet has cleared its orbit of other bodies of comparable size. Dwarf planets, on the other hand, coexist with other objects in the region of the solar system they traverse. This is the main reason why Pluto ceased to be considered a planet in 2006 and was reclassified as a dwarf planet.

Matthew Holman, a researcher at the Harvard-Smithsonian Center for Astrophysics and a member of the observatory’s operations team, identified the object on October 13 while analyzing data collected by Rubin in 2026. A more thorough search allowed the team to locate additional observations in archived records dating back to 2016. Thanks to this set of images, the team was able to reconstruct more than a decade of the object’s trajectory.

Astronomers explain that ED138 had managed to “hide” from us because its position in the night sky is against the disk of the Milky Way, which we usually see as a thick band of millions of stars. This concentrated brightness makes it difficult to distinguish fainter objects, but the Rubin Observatory’s enormous amounts of data made it possible to identify the object amid that sea of light.

Though ED138 appears to have the right characteristics, astronomers have yet to confirm whether it is a dwarf planet. For now, astronomers know it is a trans-Neptunian object, but they need to determine its size more precisely to establish whether its own gravity is sufficient to give it a nearly spherical shape. If it meets the requirements, ED138 would join the group of five dwarf planets recognized by the International Astronomical Union: Ceres, Pluto, Haumea, Makemake, and Eris.

It is also not the only celestial body awaiting possible classification as a dwarf planet. Astronomers have identified dozens of objects in the outer solar system that, based on their size and other characteristics, could meet the criteria. Among the best-known candidates are Gonggong, Quaoar, Sedna, and Orcus. Experts acknowledge that the list could be even longer.

Confirming them as dwarf planets is no easy task. The enormous distance at which they lie makes it difficult to directly measure their size and mass and, above all, to determine whether their own gravity has given them a nearly spherical shape. To obtain high-resolution images of Pluto, for example, the New Horizons probe had to be sent to its vicinity—a journey that took nearly nine and a half years from its launch in 2006 to its flyby in 2015. Three years later, it reached the object Arrokoth, a small planetesimal even farther away.

The solar system is often depicted as a star surrounded by eight planets, but in reality it is a much more extensive and populous structure. In addition to planets and moons, it contains dwarf planets, asteroids, comets, and a vast number of small bodies that extend far beyond Neptune. The Kuiper Belt extends to approximately 50 astronomical units, while the scattered disk reaches nearly 1,000. Much farther out lies the Oort Cloud, a region we have never directly observed and that could extend up to about 100,000 astronomical units from the sun.

Hackers Exploited Cisco SD-WAN Flaw to Plant Malware Built to Steal Encryption Keys

📅 Oct 29, 2026  |  Category: Technology  |  Read Source →

Hackers exploited a critical Cisco Catalyst SD-WAN flaw, fixed in February, to plant custom malware inside the systems that control an organization's SD-WAN network.

The malware, called KeyDrift, is designed to copy the keys that encrypt traffic between sites and store them for later use, Cisco Talos said on October 28. Talos calls the attacks historical but does not specify when they occurred or whether any keys were sent.

The flaw is tracked as CVE-2026-20127 and has a CVSS score of 10.0. It allows an unauthenticated remote attacker to bypass authentication and gain administrative privileges on these control systems. On a Controller, the attacker can log in as a high-privileged internal account that is not root.

When Cisco disclosed the flaw in February, Talos tracked its exploitation as UAT-8616, a cluster of activity it said went back to at least 2023.

In Cisco's traditional key exchange, each SD-WAN router periodically generates an AES key for its traffic and sends it to the Catalyst SD-WAN Controller (formerly vSmart). The Controller passes the keys on to other routers. A process on the Controller called vdaemon runs the encrypted control connections that carry these keys.

On a compromised Controller, a KeyDrift component called LittleFilch hooks into vdaemon and reads control messages after they are decrypted. For a preset list of edge routers, it pulls out their IP addresses and a 32-byte field. Talos assesses that field as the AES-256 key material that the Controller passes between routers.

LittleFilch encrypts what it collects with RSA and writes it to a file. It can then send that data over UDP to an address listed in a settings file, which it deletes after reading. Talos could not recover that settings file.

The group behind KeyDrift, which Talos tracks as UAT-11473, has targeted space and satellite services, defense and aerospace technology, and policy research.

The group's infrastructure "overlaps considerably" with Silent Train, Talos assesses with high confidence. Silent Train is the name Lumen's Black Lotus Labs uses for a network of hacked small-office, home-office, IoT and business devices.

Lumen says Volt Typhoon used the network to hide its activity. CISA, the NSA and the FBI said in 2024 that Volt Typhoon is a Chinese state-sponsored cyber group.

Talos links UAT-11473 to Volt Typhoon only through the infrastructure overlap. It does not say the two are the same group, or how UAT-11473 relates to UAT-8616, the cluster it reported in February.

Separately, Lumen said on October 28 that Volt Typhoon was exploiting CVE-2026-20127 by late 2025 and continued to exploit it after Cisco disclosed the flaw in February. Lumen does not tie that activity to KeyDrift.

KeyDrift primarily starts via modified runit scripts that Cisco SD-WAN devices use to launch their services, according to Talos. In one version, the script for the SSH service starts a loader script, conf_sshd, before the real SSH server. The conf_sshd script writes vdaemon's process IDs to a file, and a tool called rsshd injects KeyDrift's main module, PolyFlame, into each of those processes.

PolyFlame runs in memory inside vdaemon. It can act as a TinyShell-like backdoor that runs commands and reads and writes files, or as a relay that forwards commands between its command server and other machines. It is built to accept commands within SD-WAN control traffic, and the analyzed samples contained no hardcoded server address.

On a compromised Validator, formerly vBond, a fake aaamgr service under /etc/sv/aaamgr/ runs a packed loader, aaamgrd, that decrypts and runs PolyFlame. Cisco's real aaamgr component is a Python package and does not normally run as a compiled service.

There are also signs of timestomping: commands the group ran copied the timestamps and permissions of existing files onto its own files.

CVE-2026-20127 affects the Catalyst SD-WAN Controller (formerly vSmart), Manager (formerly vManage), and Validator (formerly vBond), regardless of their configuration. On-premises systems are affected, as are Cisco's hosted SD-WAN cloud deployments, including the Cisco Managed and FedRAMP environments. Cisco added the Validator to its advisory on June 16.

Cisco says it is aware of limited exploitation of the flaw. There is no workaround, and the first fixed releases are:

Releases earlier than 20.9 and the 20.11, 20.13, 20.14 and 20.16 trains have reached end of software maintenance.

Until they can upgrade, on-premises customers can limit access to ports 22 and 830 to the IP addresses of known controllers and other known systems. Cisco says this step worked in a test environment, but that customers should check how well it works in their own networks. Such guardrails are already in place for Cisco's hosted SD-WAN cloud deployments.

Blocking the ports does not remove malware already on a device.

Talos advises organizations to install Cisco's fixes, follow Cisco's Catalyst SD-WAN hardening guide and watch for signs of post-compromise activity. Anyone who finds such signs should start incident response and can ask Cisco's Technical Assistance Center (TAC) for help.

That advice does not say whether upgrading removes KeyDrift from a device that was already compromised, or whether any keys should be replaced. Cisco's February remediation guide for this flaw warns that there could be "existing exploits which are still in place" from before an upgrade.

Multigres private alpha: automatic failover for Supabase Postgres

📅 Oct 29, 2026  |  Category: Other  |  Read Source →

Multigres brings high availability to Supabase projects, and it's now in private alpha. Organizations on a paid plan can request access and create projects that run Postgres on three nodes across availability zones, with automatic failover and connection pooling included.

Today, every Supabase project writes to a single Postgres primary. This works well for most applications, and it will stay the default. The downside is what happens when the primary fails. If the underlying hardware has a fault or its availability zone has an outage, your database is unavailable until it is recovered.

Teams that can't accept that downtime usually build high availability themselves. They run replicas, add a failover manager, put a pooler in front, and write runbooks for the cases the tooling doesn't handle. The hardest part is making sure no committed writes are lost when a replica is promoted. With Multigres, Supabase takes care of all of this for you.

Multigres is an open source operating system for Postgres, built by the team behind Vitess. Vitess was created at YouTube to scale MySQL. In 2025, we announced Multigres to build the same kind of system for Postgres. We released Multigres v0.1 as open source in June under the Apache 2.0 license, and this private alpha is the first time it runs on the Supabase platform. We first showed Multigres at Supabase Select on October 2.

Multigres is not a fork of Postgres. Your data lives in standard Postgres, and Multigres manages the cluster around it: routing connections, pooling, replication, failover, and backups.

When you create a project with Multigres enabled, you get:

Most Postgres high availability tools treat failover as a monitoring problem. They detect that the primary is gone, pick a replica, and promote it. The difficult part is choosing a replica that is safe to promote. If the old primary acknowledged a commit that never reached the replica you promote, that write is lost, even though your application was already told it succeeded.

Multigres treats failover as a consensus problem instead. It uses a generalized consensus protocol built on top of Postgres synchronous replication. Your application only receives an acknowledgement for a write once it has been replicated to enough nodes to survive a failure. That guarantees every acknowledged write exists on at least one surviving node. When the primary fails, the remaining nodes agree on the full set of committed writes and make sure the replica being promoted has every one of them before it accepts new writes. This is how acknowledged commits survive a failover.

During a failover, the Multigres gateway can hold incoming requests until the new primary is ready, instead of returning connection errors to your application.

With PgBouncer, you pick a pooling mode up front. Transaction mode lets many clients share a small number of connections, but it restricts session-level features. Session mode supports those features, but each client holds a connection for as long as it is connected.

Multigres parses each request and tracks the session state it creates, so it decides how to handle every query on its own. You don't pick a mode. Each database user also gets its own pool, and a fair-share algorithm divides the connection budget across users so one busy role can't starve the others. Prepared statements are deduplicated, which means Postgres parses and caches a statement once instead of once per client. For full details on how this works, read Pooling without choosing a mode on the Multigres blog.

I have an unhealthy relationship with strategy games like these. I simply must put them through computer analysis to figure them out. I don’t know why. It’s just something that happens. I used to write tree search algorithms manually, but I have realised that OpenSpiel provides a generic tree search supporting most of the things I’ve ever found myself needing to support, so I can write the game rules in Python and hook into OpenSpiel to analyse it.

Well, consider the rules above. How often do you think the fox wins, between two equal players? Write down your guess, and you’ll learn how good your sense of this is.

The first stop for a problem like this is plain Monte Carlo tree search (mcts) with random rollouts to the end for leaf scoring. In un-optimised Python, this managed to perform about 1,000 search iterations per second when playing Starve the Fox. I gave this algorithm a thinking budget of just under a second, and played against it, both as the fox player and the sheep player. In those games, it seemed clear that the fox would win most of the time.22 Unless the sheep forced a draw, which they can do as long as there’s enough of them, thanks to the loopy nature of the game. The algorithm playing itself got a similar result: around 85 % of games were won by the foxen.

With so much corroborating evidence, I was close to calling the experiment finished. I didn’t expect deeper search to improve things by much, because the branching factor is relatively low, in part thanks to the constraints on sheep movement.

But then just to be sure, I tried one last game. I played as fox, and the computer played sheep with a search budget of 8,000 iterations. Although it still didn’t play particularly well, it managed to exploit two of my blunders, and actually get into a winning position. With the sheep! That caught my interest, and it meant the experiment wasn’t over at all, but might actually need deeper search to more accurately reflect the strategy possible.

I didn’t realise it right away, but what happened in that high search budget game was that we learned something about the nature of Starve the Fox.

The sheep side requires deeper thinking than the fox side to play well. Since the sheep, in isolated conflicts with foxes, are so underpowered, they must move the mass of the entire flock in coordination to beat the foxes, and with one movement per turn, that requires strategising over many turns.33 In fact, the sheep player isn’t really moving sheep as much as they’re moving the holes in the flock to make sure the holes stay away from the sheep closest to the foxen. This is a fantastic property of the game, because it (a) is thematically smashing, and (b) means a child can play an adult and both still have fun; the child gets to play the fox side and the adult just has to think harder.

However, I didn’t want to wait for 16,000 iterations or whatever’s needed for the plain mcts to play a very strong game. One of the more expensive parts of that search algorithm are the random rollouts to score leaves in the search tree. A trick to make leaf scoring faster is to cut off the rollouts well before the game ends44 The depth at which to truncate rollouts depends on both the complexity of the game and the quality of the rollout policy. For completely random rollouts, it may even be desirable to cut them off at depth zero – i.e. not perform any random moves at all, because they make the scored state less representative of the end state than the earlier leaf node was. In the case of Starve the Fox, stopping the rollout after 8 plies seemed to yield the best results with the first draft of the heuristic function, but it’s possible with a stronger heuristic function shorter rollouts would be even better, because they buy time for more tree search at the cost of not evaluating as far into the future., and then use a heuristic function to score the positions in games that haven’t yet terminated when the rollout is truncated. The heuristic value is scaled to be smaller in magnitude than the score given to a terminated game, so that the tree search will prioritise the win/loss signal over the heuristic when it can see both.

But this means a heuristic function is needed. A primitive one might be based on material, like “number of sheep alive” or based on progress, like “total rank gained by sheep”. A more sophisticated one might include both of those variables, and more. If we didn’t have computers, we’d probably be best off by picking out the top three variables and weighing them equally.

But we have computers, so we can do better. What we do is play the weak tree search55 Search budget of maybe 0.5 seconds per ply, scoring leaves by random rollouts to the end. against itself a bunch of times. From each of those games we sample one random position66 Only one position to avoid having to deal with the strong correlation between consecutive positions in the same game., record how the game ended, and then train a regression model to predict the game outcome based on the game state in those sampled positions. The weights we get out of the regression minimise square loss, which is probably what we want for a heuristic function.

Once we have those weights, we can create a new generation of the tree search using the same search budget, but with truncated rollouts and applying the learned heuristic function. This gets to play against the previous generation to confirm it is indeed better, and if it is, it plays itself a bunch of times again, and we sample new positions, and fit the regression again. Since it’s playing better than the previous generation, it will find ways to win from positions where the previous generation did not. Thus, the heuristic function’s prediction of outcome – assuming skilled play on both sides – will become more accurate.

We repeat that a few times, and what we get is a decently strong opponent, even at short thinking time budgets. Well, at least it reliably sweeps the floor with me, regardless of which side it plays.
