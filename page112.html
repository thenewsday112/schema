Researcher Reveals How Logic Bugs Alone Cracked Microsoft Edge in $175,000 Pwn2Own Win

📅 Oct 28, 2026  |  Category: Technology  |  Read Source →

A chain of logic flaws, with no memory corruption, can turn a malicious web page into code running on a Windows computer outside Microsoft Edge's sandbox, a security researcher has shown.

Orange Tsai of DEVCORE published the full method on October 28, five months after the chain won $175,000 at the Pwn2Own Berlin contest in May. Microsoft fixed the Edge bugs the day after the contest, so an up-to-date browser is not at risk.

A browser sandbox is the wall that keeps a web page's code inside the browser and off the rest of the computer. Breaking out of it, and then running a program, is what turns a web bug into full control of the machine.

Browser escapes like this almost always rely on memory corruption. This one used none. In his write-up, Tsai describes a chain built solely from logic errors in how Edge and Windows handle ordinary features, and he says the whole exploit is under 100 lines of code.

The result is a universal cross-site scripting (UXSS) primitive: a way to run JavaScript on any website, bypassing the content security policy meant to prevent it.

Because the attack starts from the browser's own process, it can reach sites like google.com that an ordinary web bug cannot touch. Tsai calls this a new attack surface rather than a one-off bug.

This was a competition exploit, not an attack seen in the wild. Tsai demonstrated it on stage at Pwn2Own; there is no evidence it has been used against real users, and the public CVE records list exploitation as none. One step in the chain restarts the browser, which Tsai notes is a convenience for the contest and not needed in a real attack.

The chain begins with an Edge feature for business sign-ins called a conditional access navigation throttle. Tsai found that triggering it lets the browser's own process start a new navigation that is not tied to the page that asked for it, so Edge attaches it to whichever tab is open. That mismatch is the first bug, and it produces the UXSS.

Making it run without a click took four more weaknesses. Edge checked that the request came from a trusted Microsoft site, but Tsai bypassed the check by opening the request from a second window. Edge's popup blocker should have stopped that window, but Edge carried a hardcoded list of allowed addresses, and one of them opened the popup.

The attack also required the victim to be already signed in, which the Edge auto-sign-in feature provides on its own when the user visits a Microsoft site. Lastly, the chain reads the victim's email address from a Microsoft site, assets.msn.com, which returned it to any website due to a misconfigured cross-origin setting.

Running JavaScript everywhere is still not in control of the computer. To escape the sandbox, Tsai used Edge's reading mode, Immersive Reader, which runs under a custom read:// address that Microsoft left off the list of pages barred from running scripts.

From there, the chain called an internal Edge function meant to zip up diagnostic logs and abused it to write a file with an attacker-chosen name and content anywhere on disk.

That file write is turned into code execution in two steps. The chain overwrites a configuration file that controls which websites may launch which protocol handlers, then restarts Edge so the file is read. It then launches a telnet:// link; because Windows does not ship a telnet program by default, it searches the system path for one and runs an attacker-planted copy from a folder the low-privileged user can write to.

Microsoft shipped the fix on May 15, the day after the contest, in Edge Stable version 148.0.3967.70. That release carried three Edge-specific fixes, tracked as CVE-2026-45492, CVE-2026-45494, and CVE-2026-45495. The first is recorded as a security feature bypass, and the second as a spoofing bug, both affecting Edge versions before 148.0.3967.70.

Microsoft's records rate the first two at 5.4 on a 10-point scale, a medium score that reflects a single bug in isolation, not the full chain that strings them into code execution. DEVCORE said the fix came within 24 hours of the disclosure.

Updating Edge closes this chain. Because the fix shipped in May, a browser on automatic updates has long since received it, and no separate action is needed.

Tsai built the chain by hand, over about two months, without any AI help, and frames the work as a point about where human research still matters. "The hard part is finding them, and once you find them all, chaining is the easiest part," he writes of the logic bugs. The research won the 2026 Pwnie Award for Epic Achievement.

Today, we laid out our vision for GitHub as the most comprehensive, end-to-end software delivery system in the world.

Our jobs as developers are changing. In a couple of years, we’ve gone from writing every line of code to working with AI assistants to orchestrating fleets of agents. But the goal hasn’t changed: ship completed software work. A feature, a bug fix, a security fix. Completed work, not more code, is the output that matters.

Today at GitHub Universe, we shared our vision for GitHub as the most comprehensive software delivery system in the world. We introduced products that bring that vision to life and showed how we’re rebuilding the infrastructure underneath it.

The SDLC is no longer a linear path from planning to coding to testing to deployment. A code change, a request from a colleague, or a production metric can trigger work anywhere in the system. Most of us (and our agents) jump between different stages, depending on the task at hand. Developers set the direction, make decisions, and stay accountable for what ships. Agents implement and verify changes. And everything feeds into and out of a continuous learning machine that makes the next cycle better.

This agentic software delivery system solves for three things:

GitHub is built for developers and their agents. We’re also making the underlying primitives available, so you can build your own bespoke solutions. You stay in control of the work, the tools, and the cost.

Today at Universe, we showed some of the latest products and features in action, starting with the GitHub Copilot app.

The GitHub Copilot app is designed from the ground up for agentic software delivery. It connects your agents and tools across projects, so you can direct the work without making every handoff. And it’s for more than producing code: you can write specs, present design discussions, or analyze telemetry in one agent-first surface.

Different tasks need different models. Developers shouldn’t have to manage every model choice to get the right result at the right price. Copilot Fusion evaluates what a task needs across reasoning, code generation, debugging, and tool use, then chooses how to execute across one or more models. In the Artificial Analysis Coding Agent Index, Fusion Max scored within two points of Opus 5.5 Max at half the cost and 40% less time per task.

Available natively in the GitHub Copilot app starting today, Copilot projects let you run agent work across multiple repos in fully managed, parallel sessions. You have one place to track progress, make decisions, and direct what happens next. That means you can spend less time managing execution and more time deciding what’s worth building.

Your work shouldn’t restart when you switch devices or tools. Session continuity lets you start and follow the same cloud agent session across the GitHub app, VS Code, the CLI, and the web. Start from your phone at standup, steer it from VS Code at your desk, and check in on it from github.com at lunch. The agent keeps working in the cloud. Our multi-model harness that enables it is powerful, fast, and cost-efficient.

Copilot automations let you create AI-powered workflows within your repo. They run in the cloud, and you can kick them off manually or set them up to respond to an event or run on a schedule. That lets you coordinate agents to handle tasks such as issue triage and code review. And now, automations can learn from their outcomes and propose improvements for you to review and approve. That’s the learning engine in practice. Use the results of the completed work to make the next run better.

More code means more pull requests and more demand for review. Moving faster only helps if we can maintain the quality of what ships. Copilot code review surfaces meaningful, actionable bugs that developers need to catch. Today, we introduced Copilot code review Max, which posted the highest F1 score on ReviewBench for high-severity issues. Lite and Balanced keep everyday reviews fast; the new Max provides a deeper look when a change needs it.

Starting today, GitHub Enterprise customers can use all Copilot features without buying a separate subscription. That includes GitHub Copilot app, code review, automations, and more. You pay for the AI credits you use.

This is available through GitHub Sales today, with self-serve coming soon. Existing Copilot Business and Copilot Enterprise customers can keep their current plans or move over when they’re ready. GitHub also remains open and extensible. Keep using the tools your team depends on, including Cloudflare, Datadog, Figma, and more.

All of this depends on a foundation that’s fast, reliable, and built to scale. Agents are changing the volume and shape of software development. Adding capacity matters, but capacity alone won’t get us there. We’ve also had to change the architecture.

We’re also migrating to a multi-region deployment in Azure, while continuing to serve incredible levels of traffic from developers around the world. We expect to complete the migration early next year. Those investments give us more room to grow. The next step is building the systems that handle the work.

We’ve scaled Git for years as activity on GitHub has grown. The agentic era calls for a different ceiling on throughput and reliability. Three principles guide our new Git architecture: simplify the primitives, decouple storage from compute, and minimize coordination.

Git’s just one example of the work we’re doing to scale the platform. We’ve done a lot of work across GitHub’s AI gateway, the harness, and much more.

Our jobs are changing, but developers are more important than ever. I think all the software we’ve written to date will amount to less than 1% of the software we’ll write in the next five years. The opportunity isn’t just to produce more code. It’s to solve problems we couldn’t solve before.

That’s why we’re connecting the full software delivery system, giving developers better ways to work with agents, and evolving the infrastructure for what comes next. And we’re doing it on GitHub, where we can build together.

Developers pushed code to GitHub 17.9 billion times in the past 12 months, more than in 2024 and 2025 combined.

Behind that number are developers building what interests them and what their communities need. In Nepal, one developer built a flood bulletin on GitHub Pages with verified information on roads, rescue, weather, and power. It has since grown into Gati, a Nepali-first relay of official disaster alerts that runs on GitHub Pages and Actions. Elsewhere, developers at NASA’s Jet Propulsion Laboratory are creating software designed to run programs aboard spacecraft, and fans built open-source firmware that lets people customize their e-readers. Curiosity, aimed in every direction, at a scale GitHub hasn’t seen before.

That growth happened quickly. Partway through the year, activity on GitHub bent sharply upward, just as agents went from something developers were trying out to something they were working alongside. Developers picked from more models than ever and built in industries we are highlighting in this report for the first time, from health care to agriculture.

Octoverse is our chance to step back and look at the whole picture. This year, that picture is bigger than ever. Here is what stood out most:

Underneath it all, AI models and the harnesses built around them have advanced over the past year, and developers have more to choose from. Growth is moving quickly: one year into last year’s five-year developer growth projections, every country we projected has already closed at least a fifth of its distance to 2030, and our own forecasting models no longer agree on where it will go next.

This year was all about momentum. Developers pushed code changes to GitHub 17.9 billion times in the past 12 months, more than 2024 and 2025 combined. Commits across all repo types (public and private) climbed even faster to 34.3 billion, more than three times where they stood two years ago. Merged pull requests more than tripled to 1.3 billion over the same period, an average of 3.5 million a day.

Agents were one of the tools developers leaned on hardest this year, pulling them deeper into daily work. Among repos created this year, the average repo with an agent configuration file logged eight times as many commits as the average new repo without one, sign that individuals and teams building with agents from day one are moving at a markedly different pace.

Developers also relied on automations to keep projects moving. GitHub Actions ran a job 1,440 times every second this year. This equals 124 million times a day and is more than three times last year’s total. Developers merged more than 30 million Dependabot pull requests to keep dependencies current and reduce the use of known vulnerabilities, about double 2025’s pace.

Our telemetry shows activity climbing steadily from January, then surging around June, as if developers everywhere saw new possibilities at once. Right around then, a cluster of industry-wide shifts landed: better underlying models, the harnesses and tools built around them, and the agents running on both. Agents moved from single-session tools to persistent ones that could track progress across days and orchestrate other specialized agents. Just as important, agents began making extensive use of the cloud, executing work remotely as well as on local machines.

This momentum is showing up both in brand-new repos and from developers who have been building for years. From June onwards, about 55% of all commits came from brand new repositories. But plenty more commits came from developers who’ve been around a while: developers who pushed code in the past 12 months have been on GitHub for an average of 36 months, and of those who opened a pull request in August, more than 75% pushed code in September. They are also branching out: the average developer now works across 10% more repositories than they did a year ago.

That staying power shows up in open source too. Public contributions soared to 2.5 billion in 2026, more than double last year’s total (1.12 billion). Behind those numbers are developers who keep showing up, like @kinlane, who made more than 1 million contributions across his public repositories using agentic workflows to keep a machine-readable catalog of public API information current. Another example is @kim-em, who made more than 178,000 contributions while maintaining mathlib, which is a community library of computer-checked mathematics. @andig, a maintainer of the open source EV charging controller and home energy management system evcc, contributed over 21,000 times.

These are just a few examples of the work millions of developers do every day. To all the developers doing work like this and beyond: we see you, and we’re glad you’re building.

Behind every number in this report is a developer. GitHub now serves more than 225 million of them, and the community is growing around the globe. The United States (38.3 million) and India (32 million) remain the two largest developer communities, and each added more than 10 million developers this year. Brazil added 3.28 million developers on GitHub this year, the third most of any country.

Last year, we projected that India would reach 57.5 million developers by 2030 and the United States 54.7 million. One year into that five-year window, every country in our projections has already closed at least a fifth of the distance to its own 2030 figure. The United States has closed 38.6%, and India 28.3%.

One year in, growth is strong against last year’s projection, and projecting the next five years is getting harder. We ran more than 40 forecasting models forward to 2031, time-series and regression models built on historical sign-up and usage data, each assuming a different pace of growth. About half call for “extreme” growth, with developer counts on GitHub more than tripling by 2031. Just under half call for “substantial” growth, doubling to tripling. Only three models expect anything close to modest, under 2x growth.

Forecasts are estimates, and a spread this wide shows how much the 2026 surge widened what is plausible by 2031. What holds steady is the shape of the trend: a developer community growing in more places at once.

This year, it also means more fields, including industries we haven’t measured before.

We’re sharing our view of public repositories by industry using the North American Industry Classification System (NAICS), which sorts economic activity into sectors. A language model classified random samples of public repositories created each year from 2022 to 2026, assigning each to the industry it serves based on its name, description, topics, and README. We also tracked two signals: whether a repository mentions AI, and whether an agent opened a pull request against it.

The two signals do not always move together. In administrative and support services, mining, health care, and agriculture, more than four in 10 repositories mention AI, yet agent-opened pull requests are rare, less than 3 percent. Construction breaks that pattern. About a quarter of its repositories mention AI, but about 9 percent have agent-opened pull requests, the highest share of any sector, with manufacturing next.

The same classification shows how each industry’s footprint has shifted since 2022, and sectors well beyond software are climbing. Professional, scientific, and technical services rose from fourth to second place among all industries, behind only information. Agriculture, forestry, fishing and hunting climbed two spots, and finance and insurance and health care and social assistance each moved up one. Against each sector’s own 2022 baseline, mining, quarrying, and oil and gas extraction grew roughly 65 times from a small starting base, administrative and support services and construction 17 to 18 times, and even manufacturing, the slowest of these, almost tripled.

Behind these sector shifts are people who know their fields, now using AI coding agents to build. For example, in manufacturing, a small team built a way to turn a photo of your tools into a custom-fit, 3D-printable drawer organizer. A research lab in health care made it easier for scientists to analyze huge digital scans of tissue samples, the kind pathologists study to understand disease. In Copenhagen, a university lab built a pipeline that classifies video of chickens at play, from frolicking to worm chasing. A University of Waikato energy center built a toolkit that helps industrial plants find heat they can reuse, and Bulgaria’s digital ministry open-sourced a portal where anyone can trace who won a public contract and for how much. For writers, a novelist built a free app that makes a manuscript look like a book as you type. In field after field, the people closest to the problem are building the solution, with agents helping along the way.

Professional, scientific, and technical services, which grew about 5 times over its own 2022 baseline and climbed to second place, is the work of researching, engineering, and advising, and open code has long been part of how that work gets done. In biochemistry, the work behind AlphaFold earned Demis Hassabis and John Jumper a share of the 2024 Nobel Prize in Chemistry. In computer science, Tensor2Tensor accompanied the paper that introduced the Transformer, the architecture behind today’s large language models, “Attention Is All You Need.” In medicine, sars-cov-2-stability held the code and data behind one of the earliest papers on how long the virus survives in the air and on surfaces. In physics, eht-imaging was one of two open-source libraries used to reconstruct the first image of a black hole. A repository has quietly become part of the paper trail behind published research.

More developers now begin a pull request by specifying what they want and orchestrating the agents that carry it out. By September 2026, more than 40% of pull requests on GitHub started with an agent’s first draft, up from 17% in March. That is 110 million in September alone, about 6x March’s volume.

Agent-started pull requests also more often change multiple files: about 87%, compared with 79% of pull requests without detected agent involvement. They are landing quickly too. In February, 83% of agent-involved pull requests merged within two weeks, a touch behind the roughly 86% for pull requests without detected agent involvement. By September, agent pull requests were at 90%, while the comparison group held at about 86%.

Among GitHub Copilot’s monthly active users, 55% now use agentic features, up from 35% a year ago. The steepest growth is in the most hands-off mode. Copilot cloud agent, where a developer assigns a task and an agent works on it independently, grew 230% year over year, against 85% for agent chat. Developers still ask agents questions, and increasingly they hand over whole tasks.

The willingness to delegate is reflected by the kinds of tasks developers are attempting. Public repositories mentioning interoperability or reverse engineering increased more than 300% year over year, from about 30,000 created in 2025 to more than 130,000 in 2026.

Review is where developers shape what comes back, and more tooling is being built for it. Stacked pull requests, which split related work into smaller changes that are easier to review in sequence, launched as a preview on July 30, and more than 264,000 developers had used them by September. Usage of AI-assisted code review and GitHub Advanced Security both grew more than 90% year over year. The platform also helps secure that work: push protection, which screens for exposed secrets such as API keys and passwords, ran 5.8 billion scans this year, nearly four times 2025’s pace. Developers are investing in how they review code.

Developers match models to the work they hand to their agents. In September 2026, 61% of GitHub Copilot users who selected a model themselves used more than one model across their sessions, up from 50% four months earlier.

The lineup is growing too: developers on paid GitHub Copilot plans used 29 distinct models in May and 47 in September, and no single model carried more than 25% of requests that month. Critical 16-Year-Old UEFI Flaw Can Run Code Before Secure Boot on Network-Booting Servers

📅 Oct 28, 2026  |  Category: Technology  |  Read Source →

A critical 16-year-old flaw in EDK II, the open-source code that most hardware makers use to build UEFI firmware, can allow an attacker to run code on a machine before its operating system loads, but only while the machine is booting over the network.

UEFI firmware is the software that runs first when a computer is switched on, before the operating system. An attacker who can reach the machine with a crafted network message during such a network boot can hang the boot, or, with work tailored to the exact firmware build, run their own code before Secure Boot and other startup defenses load.

An attacker needs no password and no existing access to the machine, but does need to reach it over the network during the short window when it is booting this way.

Red Hat and SUSE, which both ship the affected code, rated the flaw as one an attacker exploits from an adjacent network position rather than across the open internet.

TianoCore, the project behind EDK II, published an advisory on October 22 and rated the flaw, tracked as CVE-2026-97631, 9.5 out of 10. A code fix exists, but no stable release of EDK II contains it yet, and the advisory still lists no patched version, so most users have nothing to install today.

The flaw is a buffer overflow in EDK II's network-boot code, known as PXE. During a PXE boot, a machine loads its startup image from the network instead of from a local disk.

As part of this, the PXE driver listens for ICMP error messages and the small status messages that network devices send back, and copies each one into a fixed 504-byte area of memory.

The size checks in that copy are wrong in both the IPv4 and IPv6 versions of the code, so a message longer than 504 bytes spills past the area and overwrites nearby memory with data the attacker chose.

To set this off, an attacker only has to send one crafted error message to the machine's address while it is in the middle of a network boot. No password or existing access to the machine is needed.

The simple result is a crash: the boot hangs, and the machine fails to start. Getting code to run is much harder and far less reliable. The advisory says that an attacker who knows the exact firmware build can plant a "counterfeit event" that causes the firmware to run the attacker's own code, so an exploit has to be built for a specific build.

When code runs, it executes within the firmware, before Secure Boot and other boot-time checks have verified anything. That timing is what makes the flaw serious.

Code planted this way runs only once and does not survive a reboot by itself. That single run is still enough to install other code that does start on every boot.

The bug sits in EDK II up to and including edk2-stable202608, the newest stable version, dated August 21. EDK II is the reference code that nearly every UEFI firmware vendor builds on, including the independent BIOS makers AMI, Insyde, and Phoenix, as well as Microsoft's hardened fork, Project Mu.

The flawed copy loop has been in the code since a commit added in November 2010, The Hacker News found by tracing the project's history.

PXE network boot is turned on by default in EDK II's standard build. The flaw does not affect home or office users who boot only from a local disk. It applies to organizations whose machines boot over a network, primarily servers and data center equipment.

How many shipping products carry the vulnerable code is not known. Intel told Ars Technica that none of its "commercial products currently under security support" are known to be affected, and that it "does not include the affected EDK2 functionality in its reference code," though an OEM board vendor or system maker could add it.

Arm said the flaw "is not directly applicable to Arm's product portfolio." Both companies' own firmware draws on EDK II.

Linux distributions also ship the code. Red Hat lists its edk2 package in Red Hat Enterprise Linux 8, 9, and 10 as affected and not yet fixed, and SUSE and Debian mark their equivalent packages the same way.

AMD, Phoenix Technologies, AMI, Microsoft, and Amazon did not answer the tech news site's questions before publication, and TianoCore did not respond either, so the status of their products remains unclear.

A fix has been merged into the EDK II source code. It rewrites the faulty copy so an oversized message is cut off at 504 bytes instead of spilling over, and it reached the main development branch on October 15.

No stable release of EDK II includes that fix yet. The Hacker News checked the project's release tags on October 28 and found the newest, edk2-stable202608, predates it, and the advisory still lists the patched version as "Not patched currently." Microsoft's Project Mu has already pulled the fix into its release branches, and cut tagged builds on October 26.

Even with the fix public in source, a server operator has nothing to install until the maker of their firmware ships a BIOS or UEFI update built from it. That step is at least straightforward, Jesse Michael, a principal researcher at the firmware security firm Eclypsium, told Ars Technica: unlike Secure Boot bypasses such as BootHole and BlackLotus, the flaw "can be fixed with a basic code fix" and does not require certificate or key revocations.

Until that update arrives, the advisory lists no workaround. Because the flaw can only be reached during a network boot, operators who do not need PXE can disable it to reduce exposure. Ars also advised watching boot-time network traffic and logs for signs of attempts.

The flaw was found by Alex Matrosov of Anthropic and Dan Holmes-Mitra of Google, the advisory credits. A coordinated disclosure had been planned for January 2027.

That plan was overtaken on September 28, when a pull request to EDK II, signed off by an AMI engineer, publicly described the flaw by its CVE number and included the fix. Once the people who found it saw the post, TianoCore published its advisory on October 22, weeks before the planned date.

With the patch public, Ars noted that skilled attackers can study it to determine how the flaw is triggered and build working exploits.

There is no sign the flaw has been used in an attack. It was not in CISA's Known Exploited Vulnerabilities catalog as of its October 27 update, and no researcher has reported seeing it exploited.

The flaw is also not, on its own, a way into a network, Ars Technica reported after putting questions to several firmware researchers. The realistic attacker is an insider, or someone who has already gained a low-level foothold on the local network and wants to dig deeper.

"An attacker intent on compromising a nearby endpoint or server could use this bug to hijack program flow at a point where the boot process still has access to sensitive components, like the endpoint's TPM," said HD Moore, the creator of Metasploit and chief research officer at the security firm Dragos, in comments to Ars Technica.

"This could be used to break disk encryption for cases where an attacker has short-term network access (and it would be even easier in a theft scenario)."

It is not the first serious flaw in EDK II's network-boot code. In January 2024, researchers disclosed PixieFail, a set of nine flaws in the same part of EDK II, also reachable during PXE boot. Ars reported that fuzzing projects started after PixieFail to find more bugs in the code did not catch this one.

Sauerkraut at Every Meal? These Fermentation Fanatics Tried That Long Before MAHA

📅 Oct 28, 2026  |  Category: Technology  |  Read Source →

Waking early, I put a small jar of my sauerkraut into my messenger bag, hop on my bicycle, ride to Seattle's King Street Station, and board a train heading to the Portland Fermentation Festival, the yearly gathering affectionately nicknamed “Stinkfest.”

Usually the sheer existence of a festival like this is enough to get people revved up to come together and talk about their favorite ferments, but in an interesting twist, fermented foods are enjoying a popularity boost from a different crowd. The MAHA movement, and particularly the Donald Trump cabinet, are big into fermented food, eating meat, usually steak, with fermented sides like kimchi or sauerkraut at every meal.

I've come to Portland, Oregon, wondering if there was going to be any overlap in the Venn diagram between festival attendees and the MAHA steak-and-ferment crowd. I mentioned this to my cousin-in-law Erick, who's been part of the Portland food scene for years, and he laughed out loud.

“It'll be more like a Venn dumbbell,” he said, making a pair of thumb-and-forefinger circles and tracing a line in the air between them. “No overlap, but food will be the bridge.”

The festival is almost exactly what the fermentation-friendly might hope to find. Right inside the main door next to the check-in desk is a bacterial petting zoo—pure festival charm—and a table where attendees can drop off their own ferments to share. Further on, lining every wall of the main room, are exhibitors who have paid a grand total of 25 bucks for a table, handing out free samples of fermented foods.

The space quickly fills up–several hundred people flow through over the course of the evening–and it appears that there's both a line in front of each exhibitor and perhaps a more organic continuous line with people flowing clockwise from one exhibitor to the next. People are notably excited and happy. There's a kid walking around with a tray of handmade pickle pins he's giving people to wear and there's a collective gasp when 20 or 30 minutes in, Dillon T. Pickle, the mascot of the Portland Pickles West Coast League baseball team, walks into the room. At one point, a big baby crawls across most of the main floor, unhindered and happy.

In the middle of it all is festival co-organizer, journalist, and cookbook author Liz Crain. She explains that the Fest, now in its 14th installment, was started in 2009 by friends who love to ferment. There were members of a little company called Picklopolis and a club called The Kraut Collective, and, with some help from author and fermentation rockstar Sandor Katz, they launched a Portland tradition.

When I ask how the festival has evolved since its first year, she gets a little philosophical.

“Keep Portland Weird. People get excited,” she says in a tone where several punctuation options would be in the spirit of the festival. “People lined up on the sidewalk all the way around the building for the first one. I poured hard cider that I made from a tree in my backyard.”

“There's nothing for sale, and that gives it a potluck-y party style. Most big festivals have consumers and purveyors, but without those distinctions here, it makes conversations a bit deeper, a bit more personal,” she says. “There's no gatekeeping, no secret recipes. It's always been wacky and fun.”

She isn't sure how much MAHA crossover I'll encounter, but she has an openness to it.

“RFK is certainly infatuated with sauerkraut and steak. There's some good to be found in the overall MAHA tenets, but so much of it has been muddied by the anti-vax stance and ludicrous conspiracy theories,” she says, though she believes it's important to “look closely and critically at pesticides and favor less-processed foods.”

“But a diet that's based solely on meat, particularly beef, animal fats, and sauerkraut … well that's not a very diverse diet,” she says. “Let's just say I wouldn't want to sit next to that person on a plane or be stuck in an elevator with them.”

I pick up on these ideas with Chris Curtin, a fermentation microbiology researcher at Oregon State University.

“Historically, everything has shown that narrowing the scope of your diet misses some things. They don't turn out to be the best in the long run,” he says. An Australian living in the US for the last decade, he can clearly see the way trends are moving and notes that registered dietitians have consistently put fermented foods at the top of their superfood lists for the past decade.

Curtin describes his work as caring about what happens when we mess around with microbes to see what happens to the raw material. As he puts it, "I'm interested in tinkering if it involves microbe wrangling." He also gets the festival's popularity among those who ferment.

“Fermenting is such a readily accessible scientific experiment that you can do in your kitchen. People go, find foods they like and want to make in their own kitchens. It's accessible and tactile.”

This plays out at the festival as I begin to sample the merchandise. The first thing I taste is an “orange whey Julius” that includes whey and OJ and is pleasingly reminiscent of the Orange Julius I'd get as a treat as a kid at the Mall of New Hampshire.

Next to that is Nat West's booth with Peruvian corn beer called chicha. West has run a cider company, dabbled in politics, driven a TriMet city bus in Portland, and now runs the Vancouver, Washington, farmers’ market. In a chicha, the fermentation starts by the brewer chewing ground field corn. At the festival, attendees are drinking what West has chewed. As people in line joke about drinking this guy's spit, or at least the byproducts of it, West interjects, “nobody's died yet!”

“The ptyalin enzymes in the saliva kickstart the starch-to-sugar process,” he explains as I take a sip and gaze longingly at the draft beer in the hands of someone who's wandered into the show from the Hotlips pizza next door.

Further along, Portland's Jorinji Miso has a double booth with samples of miso soup with bonito flakes along with koji (rice fermented with Aspergillus oryzae spores) and amazake, a koji-based drink.

The couple who run Maypop Wine Co. have their hands full at the Fest. The company’s cofounder Vince Kelsea explains that they make “anything but pinot” in the Willamette Valley—a lush north-south valley in Oregon renowned for its pinot noir. Making unfiltered, low-intervention wines like Maypop in a region famous for its pinot sounds like they're making things hard for themselves, but the attendees maintain a several-deep line at the booth all night long.

In one corner is Kiyomi Hasagewa, a third-generation Japanese bean purveyor. She’s sharing tastes of a 15-year-old miso she dehydrated and ground so she could bring it from Hokkaido to the festival. She sprinkles it over the rice and tops it with a wedge of sun-dried daikon which her elderly mother fermented in a mashed pumpkin paste. It is easily the most interesting bite in the room.

Back in the entry hall are my personal favorites, the ferments that attendees have brought to share. Liz Crain has brought along plum and dandelion wines, pickle brine, a blackberry-blueberry-lemon water kefir, and a monster jar of sour dills. I note with pride that the jar of sauerkraut I brought is next to Liz’s pickles, near-empty. Nearby is another giant jar of “fermented carrot coins, cherry bomb, garlic, ginger, horseradish,” which I anticipate as a pleasant assault on my senses, but it's really just pleasant. A garlic blast for sure, but one with all of the harsh edges smoothed by time and beneficial bacteria into something lovely.

Also at the community table are Portland occupational therapist Eva Ortega and her fermentation buddy Letti Kittel who drove down from Seattle.

“I've only made unsuccessful ferments so far,” says Ortega, undeterred. “I'm here to learn.”

Kittel says she's been nerding out on fermenting for about a year and has brought a kombucha starter with its bacteria-and-yeast scoby for others to bring home and try. And while both of them have no comment about the MAHA connection, Ortega puts some of Kittel's starter in a little jar and drops it into her purse.

I'm expecting another round of “no comment” when the MAHA diet comes up with three other fermenting friends, Megan Andricos, Josh Monifi, and Desiré Demarest, but Andricos, aka DJ Sappho, followed a similar diet 20 years ago in what they call their “fermented-pickled food and protein phase,” which consisted of “mostly kimchi and meat.”

They're off that diet now, but they liked being on it. “Kimchi evens out my gut biome. I felt better. Not superhuman, but better.”

Also on the community table is something called “Higgins Kraut,” made with Napa cabbage, carrots, garlic, and ginger, which, with a lovely melding of flavors, won my personal Best-in-Show award.

Turns out it's made by one of the show’s other founders, George Winborn, who was involved for the first 10 years. He'd been farming in Dallas when he moved to Portland, to a place that had no yard and nowhere to farm.

“Doing the Fest helped scratch the itch,” he says. He's now getting Wellspring Farm in Gresham, Oregon, off the ground and noted how the festival has become a bit more commercial, a bit less homemade. But all that's relative, considering we're standing here over our jars of sauerkraut, and the exhibitors are very small businesses, if they're businesses at all.

“I still love the DIY and starter tables,” he says. “It reminds you that everyone can do this.”
